## 1. 决策 D1：用校验和替代手动版本号

### 1.1 为什么必须换

现行（05 文档）的设计是：`manifest.json` 里每个文件带一个 `version`，改了内容要**手动 +1**。  
这是 ClassIsland 官方文档反复警告、也是实际使用中最常见的失效模式：

- 忘了加版本号 → 客户端认为"没变" → **永远不更新**，而且**没有任何报错**，只能靠人去教室机上看出来；
- 加了版本号但内容没变 → 全量重下，浪费流量；
- 多人协作时版本号还会冲突/回退。

改成**内容校验和**后：内容变 → 校验和变 → 客户端必然感知。**零人工、零遗忘**。

### 1.2 算法选择

| 算法          | 结论                                                      |
| ----------- | ------------------------------------------------------- |
| **SHA-256** | ✅ 采用。.NET 内置 `SHA256.HashData(stream)`，几十 KB 文件耗时 < 1ms |
| MD5         | 不必。Xibo 用 MD5 是早年兼容考虑；我们没有历史包袱，直接上 SHA-256              |
| 文件大小 + 修改时间 | ❌ 不可靠（复制/同步会改时间戳）。仅作辅助快速预判                              |

### 1.3 清单（manifest）结构

**关键设计：按班切分清单，而不是全校一张大表。**  
原因：全校一张表约 90 条 × 200B ≈ 18KB，每 10 分钟拉一次、30 台机器一天就是 ~78MB；走网盘 WebDAV（坚果云免费额度 3GB/月）几天就爆。按班切分后，每台只拉自己那份（约 0.5KB）。

- 位置：`<分发根>/m/<grade>-<序号>.json`，如 `m/g7-01.json`
- 命名用 `g7/g8/g9` + 两位序号，**避免中文和括号进 URL**（`七年级(1)班` 在 URL 里要编码，易错）；清单内部记录 `className` 便于对账。

**清单样例**：

```json
{
  "schema": 2,
  "className": "七年级(1)班",
  "classKey": "g7-01",
  "generatedAt": "2026-10-31T06:00:12+08:00",
  "termStart": "2026-09-01",
  "pollMinutes": 10,
  "weekStartDay": "Sunday",
  "files": [
    {
      "key": "base",
      "path": "d/g7-01.json",
      "sha256": "9f2c...（64位）",
      "size": 23451,
      "updatedAt": "2026-10-31T06:00:12+08:00"
    },
    {
      "key": "subs",
      "path": "d/subs.json",
      "sha256": "1a77...",
      "size": 812344,
      "updatedAt": "2026-10-31T06:00:12+08:00"
    },
    {
      "key": "term",
      "path": "d/term-g7.json",
      "sha256": "33b0...",
      "size": 612
    }
  ]
}
```

**`weekStartDay`：学校推荐值（可选字段）**

主机在清单里下发 `"weekStartDay": "Sunday" | "Monday"`，教室机首次接入时**跟随该值**；
之后若本机手动改过，则**以本机设置为准**（不清洗用户选择）。这样 30 台开箱一致，个别班想改也不冲突（§3.8）。

**`key` 的语义**（决定客户端怎么消费该文件）：

| key    | 内容                                                      | 说明                                             |
| ------ | ------------------------------------------------------- | ---------------------------------------------- |
| `base` | 该班基础课表（含单双周、教师、地点、节次时间）                                 | 每班一份，必选                                        |
| `subs` | **全校调代课原始记录**（带 `validStart/validEnd/srcSlot/destSlot`） | 全校共用一份，客户端按自己班过滤；**必须是原始记录，不能是已展开的结果**（见 §3.4） |
| `term` | 年级时间表 + 固定项（大课间/眼保健操/午休）                                | 每年级一份，可被多班共用                                   |
| `xlsx` | 电子表格原文件（B 路备用形态）                                        | 客户端本地用现有 `ScheduleImporter` 解析                 |

> 为什么 `subs` 下发"全校原始记录"而不是"本班已过滤结果"：  
> 一台机器今天部署、下周才开机，或显示日期被手动切到别的周，用"已过滤结果"就会错。  
> 下发原始记录 + 客户端按显示周展开，才能保证**任何时间打开都正确**。

### 1.4 客户端比对与下载流程

```
每 pollMinutes（默认 10 分钟）或启动时：
  1. 取清单（按源类型：HTTP GET / File.ReadAllText / WebDAV GET）
      失败 → 保留本地缓存，指数退避（1×→2×→4×→封顶 4×间隔），记录"最后成功时间"
  2. 清单解析失败 / schema 不符 → 视为"无更新"，不覆盖本地缓存
  3. 对每个 entry：
       若本地 <key> 的 sha256 == entry.sha256 → 跳过（不下载）
       否则 → 下载到 <key>.tmp → 校验 sha256
               ✅ 一致 → 原子替换（File.Replace / Move），更新本地元数据
               ❌ 不一致 → 丢弃 .tmp，保留旧文件，记录告警（本轮不采用新数据）
  4. 全部成功且至少一个文件更新 → 触发"重新构建课表"
```

**四个必须遵守的细节**：

1. **先写 `.tmp` 再原子替换**——防止下载中断留下半截文件（最容易被忽略、也最容易造成"课表突然空了"）。
2. **校验失败保留旧文件**——绝不因为新数据坏了就把旧数据删掉。
3. **缓存里存一份 `last-good/` 备份**——成功构建后把当前有效文件集复制/硬链到 `last-good/`；连续失败时回退到它。
4. **exe 启动首帧先用缓存渲染**，再异步检查更新——不要让网络阻塞界面（教室机开机就要显示）。

## 2. 决策 D2：CSES 导入 / 导出

### 2.1 字段映射（已核对官方 `cses.schema.json`）

CSES v1 顶层只有 `version` / `subjects` / `schedules` 三个字段。

| 我们（ScheduleCore）    | CSES                                            | 备注                                    |
| ------------------- | ----------------------------------------------- | ------------------------------------- |
| `Lesson.Subject`    | `schedules[].classes[].subject`                 | **是字符串名**，必须能在 `subjects[].name` 里找到  |
| `Lesson.Teacher`    | `subjects[].teacher`                            | ⚠️ 教师挂在**科目**上，不挂在具体一节课上（见 §2.3 边界 2） |
| `Lesson.Location`   | `subjects[].room`                               | 同上                                    |
| `Lesson.Week` 0/1/2 | `schedules[].weeks` = `all`/`odd`/`even`        | ✅ **天然对齐**，不需要自己造语义                   |
| `dayIdx` 0..6       | `schedules[].enable_day` = 1..7                 | 我们 0-based → 加 1                      |
| `Lesson.TimeRange`  | `classes[].start_time` / `end_time`（`HH:MM:SS`） | CSES **用时间定位，不用"第几节"**                |
| 班级                  | ——                                              | **CSES 没有班级字段**                       |

### 2.2 一份 CSES = 一个班

CSES 没有班级概念，所以导出时**按班生成 30 份**（每台教室机只需自己那份，正好契合分发模型）。  
文件名建议 `班级名.cses.yaml`，放在 `d/cses/` 下。

### 2.3 三个必须说清的边界（决定它只能当"交换格式"，不能当分发主格式）

1. **CSES 表达不了调代课**。它没有日期、没有生效区间、没有"原位置/目标位置"。  
   → 所以调代课**继续走我们自己的 `subs` 文件**，CSES 只承载"基础课表"。
2. **科目与教师绑死**：`subjects[].teacher` 是单值。若同一科目由两位老师分别教不同班（现实中很常见），  
   合并成一份 CSES 就必然冲突。→ 我们导出时**按班导**（一份只含该班用到的 subject），冲突自然消失；  
   但**导入**别人做的 CSES 时，若发现同名科目教师不同，需要提示"以 CSES 中的 teacher 为准"。
3. **只有时间、没有节次**：导入时要靠 `term` 里的节次时间表**反查**回"第几节"。  
   若某节时间与 CSES 里的时间**不完全相等**（比如改了作息 5 分钟），需要做**最近匹配**并给出警告，不能静默丢弃。

### 2.4 定位

- **导出 CSES**：✅ 做。轻量、有价值——可作为备份、可交给 ClassIsland / Class Widgets / 凌云使用。
- **导入 CSES**：✅ 做，但作为**第二数据源**（教务若愿意用现成 CSES Web 编辑器改课表，就能绕开腾讯文档）。
- **分发主格式**：❌ 不用 CSES。分发继续走自定义 JSON（能承载调代课、能带校验和）。

## 3. 决策 D5（核心之一）：按"显示周"过滤生效期

### 3.1 实测数据（2026-10-31，全校三档合并去重后 4070 条）

| 指标                                   | 数值                                                                         |
| ------------------------------------ | -------------------------------------------------------------------------- |
| 原始记录（三档合计）                           | 4194，去重后 **4070**                                                          |
| `status = 已失效`                       | 3439                                                                       |
| `status = 生效中`                       | **631**                                                                    |
| 生效区间的跨度（`validEnd - validStart + 1`） | 1 天 17 / 2 天 23 / 3 天 203 / 4 天 476 / **5 天 2116** / 6 天 554 / 7 天 681     |
| 最常见的区间                               | `2026-10-26 ~ 2026-10-30`（493 条）、`10-19 ~ 10-23`（393）、`10-12 ~ 10-16`（391） |

**结论 1：一条调代课记录 = 一个"周区间"，不是"某一天"。** 绝大多数是周一到周五整段。

### 3.2 现有代码的 bug：按"今天"过滤，周末会误删整周调代课

现有 `ErYiClient.BuildFromCache` 用的是：

```csharp
var today = DateTime.Today.ToString("yyyy-MM-dd");
if (s.ValidStartDate.CompareTo(today) > 0 || s.ValidEndDate.CompareTo(today) < 0) continue;
```

今天是 **2026-10-31（周六）**，而本周调代课 493 条的 `validEnd = 2026-10-30（周五）`：

| 判断                          | 结果                       |
| --------------------------- | ------------------------ |
| `status = 生效中` 的记录          | 631 条                    |
| 其中 `validEnd < 今天`（被现有代码砍掉） | **493 条** ← 全是**本周**该显示的 |
| 其中真正覆盖今天（周六）的               | 138 条                    |

也就是说：**周六、周日打开教室机，本周一~周五的调代课全部消失**，界面回到"原始课表"，老师看到的课是错的。  
反过来，若改成"本周全放行"又可能把上周记录带进来（上周 393 条 `10-19~10-23`）。

**结论 2：过滤基准既不能是"今天"，也不能是"整周不过滤"，而必须是"显示日所在周的每一天"逐日判断。**

> **r8 已修**：`ErYiClient.BuildFromCache` 里的 `today` 过滤已删除，改为把 `validStartDate ~ validEndDate`
> 原样写进 `LessonOverride.ValidFrom/ValidTo`，由 `OverrideExpander` 按显示日期求交。
> 效果：周六 / 周日打开，周一到周五的调代课不再消失；上周的记录也不会串进来。

### 3.3 正确模型

```
显示日 displayDate（= 今天，或设置里的固定显示日）
  ↓
weekStart = 按「周起始日」配置取 displayDate 所在周的起点
            （★ 默认周日；可改回周一，见 §3.8）
  ↓
weekDays  = [weekStart, weekStart+1, …, weekStart+6]     ← 7 天窗口
  ↓
对每条调代记录 s，遍历窗口内每一天 date：
      若 s.ValidFrom <= date <= s.ValidTo  →  该条在 date 对应的星期几生效
  ↓
DayIdx = 该日期对应的日历星期（周一=0 … 周日=6）
         ★ 与"它在窗口里排第几天"无关（周起始日设为周日时二者不同）
  ↓
生成 LessonOverride { DayIdx, Period = destSlot % 8 + 1, ... }
```

**举个具体的**：

| 记录 | 生效期           | 显示周 = 10-26(一) ~ 11-01(日) 的展开结果 |
| -- | ------------- | ------------------------------- |
| A  | 10-26 ~ 10-30 | DayIdx = 0,1,2,3,4（周一~周五）       |
| B  | 10-29 ~ 10-30 | DayIdx = 3,4（只有周四、周五）           |
| C  | 11-02 ~ 11-06 | **不展开**（下周，本周不显示）               |
| D  | 10-19 ~ 10-23 | **不展开**（上周，已过期）                 |

这样"过期的不显示"和"本周该显示的都在"同时成立。

> 上表按**周一为起始**举例。若把周起始日设为**周日**（见 §3.8），窗口会整体前移一天，  
> 但"某条记录落到星期几"的结果不变——变的只是**哪些天被算进"本周"**。

### 3.4 架构要求：缓存必须存"原始记录"，不能存"展开结果"

这是本节最关键的一条，也是最容易埋雷的地方。

|                                                                      |        |                |
| -------------------------------------------------------------------- | ------ | -------------- |
| 现在的流程是：`BuildFromCache` 里按今天过滤 → 展开成 `LessonOverride`（只有 \`ClassName | DayIdx | Period\`）→ 存盘。 |
| **问题**：`LessonOverride` 丢掉了日期。一旦存成这个样子：                              |        |                |

- 10-31 抓的数据，11-02（下周一）开机 → 存的是上周展开结果 → 显示的还是上周的调代课；
- 教室机显示日被切到别的周 → 完全对不上。

**改造要求**：

| 数据                   | 存什么                                                                                            | 何时展开                 |
| -------------------- | ---------------------------------------------------------------------------------------------- | -------------------- |
| `subs`（二一下发）         | **原始记录**：`className / srcSlot / destSlot / subject / teacher / validStart / validEnd / status` | **渲染时**按"显示日所在周"动态展开 |
| `import`（Excel 临时课表） | 原始覆盖项 + `ValidFrom/ValidTo`                                                                    | 同上（统一走展开器）           |
| `manual`（本地手工）       | 原始覆盖项 + `ValidFrom/ValidTo`（见 §4）                                                              | 同上（统一走展开器）           |
| 展开结果                 | **不落盘**（或只缓存当周，带 `weekKey`）                                                                    | ——                   |

即：**所有临时层都只存"带区间的原始记录"，渲染时才展开**。这样 30 台机器即使显示不同日期、不同周，也都各算各的、互不影响。

### 3.5 `status` 与日期冲突怎么办

实测：`status = 已失效` 但日期仍覆盖本周的只有 **3 条**（占 0.07%），说明二一的 status 与日期**基本一致但会滞后**。

采用**日期为准、status 兜底**：

```
若 status == "已失效" → 仍以日期区间为硬条件
                        （不单独用它砍数据，见下）
否则 → 以日期区间为准
```

保守做法（推荐）：**日期区间是硬条件；`status=已失效` 不单独用来砍数据**。  
理由：误删一条该显示的调课（老师走错教室）比多显示一条后果严重得多。

### 3.6 跨周记录

`span >= 7` 的只有 **4 条**（比如连排两周的教研活动）。逐日判断天然支持，无需特殊处理。  
但要注意：这类记录会在两个显示周里**都被展开**，这是正确行为（本来就该连两周生效）。

### 3.7 顺带要确认的一个缺口：调课的"原位置"

`srcSlot != destSlot` 的"调课"意味着课从 A 节挪到 B 节。现有代码**只在 B 节写了覆盖，A 节仍显示原科目**（`IsEmpty` 字段存在但没用上）。

建议（列为可选项，不混进本次主线）：

- 调课生效时，`srcSlot` 对应位置标记为 `IsEmpty = true`，界面显示"（调至周X第Y节）"而不是继续显示原科目。
- 否则老师会看到"这节课还在，但老师已经去了别的班"。

### 3.8 周起始日可配置（**默认 = 周日**，可改回周一）

**为什么需要这个选项**

周日就要开始准备周一的课。若"本周"固定从周一算起，**周日打开时看到的还是上一周**
（窗口 10-26 一 ~ 11-01 日），周一的课落在"下周"，调代课既不展开、周序号也对不上。

把周起始日设为**周日**后，"本周"变成 `11-01(日) ~ 11-07(六)`，周日当天就能看到：

- 周一到周五的完整课表；
- **下周一的调代课已经生效**（`validStart = 11-02` 的记录能落进来）。

**定稿：默认值取"周日"**

| 项 | 值 |
|---|---|
| 默认值 | **周日**（`WeekStartDay = Sunday`）。全校 30 台开箱即用，周日打开就能备下周课，不需要逐个改设置 |
| 可选项 | 周一（`Monday`）——给"习惯按周一翻页"的老师 |
| 设置位置 | 显示设置页 →「一周从哪天开始」（见 §3.8 末） |
| 周序号影响 | **无**。两种设置下 11-02 都是第 10 周 |

> 为什么默认值选周日而不是周一：大屏的**主要用户场景就是"提前看"**（周日晚/周日到校看明天上什么）。
> 若默认周一，每台机器都要人工改一次，且在改之前周日永远是"上一周"，属于默认失效的状态。
> 代价是"周日的课"在窗口里排在**最后一天**（`DayIdx=6`），需要 UI 上把周日列弱化——见 §3.8 末"周日列的处理"。

> **⚠️ r8 实现状态（重要，别误解）**：本轮**只落地了"生效区间"本身，周起始日仍固定为周一**
> （`WeekHelper.DefaultWeekStartDay = Monday`，`WeekHelper.WeekWindow()` 已支持传入起始日，但目前所有调用都传默认值）。
> 原因：周视图 / 周课表的列映射（`WeekBuilder` 的 `dayIdx = 0..6`、`WeekView.StartOfWeek`）
> 全部按"周一打头"写死，若只把"本周"改成周日打头，会出现**表头写 10/26–11/01、生效区间算成 10/25–10/31** 的对不上。
> 两者必须一起改（属 P1b），本轮不动，以免把显示搞乱。

**窗口定义**

| 周起始日 | 第 k 周窗口 | 以 11-01 为例 |
| --- | --- | --- |
| **周日（默认）** | 周日 ~ 周六 | 打开 11-01(日) → 属第 10 周 `11-01 ~ 11-07` |
| 周一 | 周一 ~ 周日 | 打开 11-01(日) → 属第 9 周 `10-26 ~ 11-01` |

两种都是 7 天，差别只是**左边界前移一天**：

```
周日起始的第 k 周 = 周一始的第 k 周 ＋ 前一个周日 － 后一个周日
```

**关键：周序号不会因此跳变**

周日起始的第 k 周窗口里，那个周一（11-02）**仍然是"周一始"的第 k 周周一**。
所以 `第N周` 的结果在两种设置下完全一致 —— 11-02 都是第 10 周。

> 这正是选"只把左边界前移一天"、而不是"把整周整体向前平移"的原因：
> 整体平移会让大屏上的"第N周"和学校口径打架（同一天显示不同周次，很难解释）。

**必须一起改的三处（否则自相矛盾）**

| 位置 | 为什么要改 |
| --- | --- |
| `OverrideExpander` 的窗口起点（§3.3） | 决定"哪些日期参与展开" |
| 手工修改的默认生效周（§4.4） | 周日起始时，周日改的课应默认归入**即将开始的新一周** |
| 周视图 / 日期切换窗口的"本周"范围 | 显示的范围要和展开窗口一致 |

**绝对不要改的地方（最容易写错的一行）**

- `DayIdx` 仍然是**日历星期**（周一=0 … 周日=6），**不能**把"窗口里第 0 天"当成周一。
  周日起始时，窗口第 0 天是**周日**（`DayIdx = 6`）；若写成 `DayIdx = 位置`，整张课表会**错位一天**。
- 单双周（`Lesson.Week`）判定不受影响：它按"教学周奇偶"算，与窗口起点无关。
- **`WeekHelper.TeachingWeek()` 内部必须继续按"周一"算周序号，绝不能把 `WeekStartDay` 传进去。**
  `WeekStartDay` 只影响 `WeekWindow()`（显示/展开窗口），不影响 `TeachingWeek()`（第几周）。
  两个函数职责必须分开，否则默认周日会让**周序号整体偏移一周**（周日并入下一周，全学期都错）。

**设置项**

- `AppSettings.WeekStartDay`：`Sunday`（**默认**）/ `Monday`。
- 界面位置：**显示设置页 →「一周从哪天开始」**（定稿，不放数据页/课表页）。
  旁边一行说明：`周日开始：周日即可查看下周课表（推荐）；周一开始：与学校周历一致。`
- 变更时**立即重算**当前课表，并给一句确认回显：
  > `本周范围已调整为 11/01 – 11/07，周序号仍为第 10 周。`
- 建议随分发下发一个"学校推荐值"（清单里的可选字段 `weekStartDay`），教室机默认跟随、也允许单独覆盖 ——
  这样 30 台初始一致，个别班想按自己习惯改也不冲突。

**周日列的处理（周日起始后必须决定的一个界面细节）**

周日起始时，窗口内周日的课会排到**最右/最后**，而多数班级周日**没有课**，会让大屏看起来"多出一列空白"。两种处理：

1. **推荐**：周视图固定按 `周一…周五` 排序显示，周日**只在与调代课/课程有关时**才出现在末列（并在该列标题标"周日"）；
2. 或：周视图仍按窗口顺序显示（周日打头），但把周日列宽度压到 60%，无课时显示 `—`。

无论哪种，**排序只影响视觉，`DayIdx` 永远是日历星期**，两者不能混。

**边界情况**

| 情况 | 行为 |
| --- | --- |
| 默认周日 + 周六打开 | 属"上一周"（`10-25 ~ 10-31`），周六不备下周的课；若也要看，靠 §3.9 预览 |
| 学校周日有课（workday 含周日） | 周日按 `DayIdx = 6` 正常参与展开；此时周日列会被填充，按上面的规则显示 |
| 学期首周 | 首周窗口从 `termStart` 当周起点算；无论哪种设置，周序号都是第 1 周 |
| 跨年/跨月 | 窗口按日期连续推算，不按"周数"硬编码，农历/公历无影响 |

### 3.9 "预览下一教学日"（每天生效、可开关，D12 修订）

**改动要点**：不再只限周末、不再"必做"。改为——

> **每天**都判断一次：只要「**当天没课**」或「**当天课已上完**」，就把屏切到**下一个有课的日子**；
> 是否启用由开关决定，老师可以关掉。

这样"放学后大屏显示明天"与"周末显示周一"变成**同一个规则**，不用两套逻辑。

**触发判定（按顺序，任一成立即预览）**

```
① 今天整列无课（周末/假期/全天调空）        → 立即预览
② 今天有课，但 now >= 当天最后一节结束 + grace(默认15min) → 预览
③ 其余情况（正在上课 / 还没到第一节课）      → 显示今天，不预览
```

**★ 关键：判断"最后一节"必须用"展开后的当天课表"，不能用 base**

因为调代课会把当天后面的课调空、或提前放学。若拿 base 算，遇到"下午全调空"的日子，
屏上会一直停在一张已经没有课的课表上，直到 17:15 才跳。

```
当日有效课 = EffectiveBase ⊕ 各启用层（按优先级）
lastEnd = max(该日所有"非调空"课节的结束时间)      // 一节都没有 → 走 ①
```

**开关与参数**

| 设置项 | 值 | 默认 |
| --- | --- | --- |
| `PreviewNextSchoolDay` | `Off` / `On` | **On**（可关，关掉后严格显示"今天"，没课就显示"今日休息"） |
| `PreviewGraceMinutes` | 0–60 | **15**（下课铃响后留 15 分钟，避免正在收拾时屏幕跳变） |

**向后找"下一个有课的日子"最多 15 天（不是 7 天）**

原设计写"最多 7 天"，遇到**国庆前一天放学后**会找不到（10-01 到 10-07 全无课，第 8 天才上课），
结果不预览、直接显示"今日休息"，反而更差。改为 **15 天**，覆盖国庆 + 中秋连休。

```
从 今天+1 起，最多 15 天：
  跳过 该星期几整列无课 的日子
  跳过 该日全部节次"调空/停课" 的日子
  取第一个"至少 1 节有效课"的日子 → 预览日
  15 天都没找到 → 不预览，显示"今日休息"
```

**与「固定显示日」的优先级（不变）**

| `DisplayDateMode` | 预览开关 | 行为 |
| --- | --- | --- |
| `Today` | On（默认） | 按上面三条判定，标题带 `预览：` 前缀 |
| `Today` | Off | 严格显示今天 |
| `Fixed` | 任意 | **固定日优先，不预览** |

**标题与切回**

- 标题：`预览：11-02 周一`（灰底/小号，和真实"今天"区分）；
- 双击标题 → 切回"今天"并**关闭本次预览**（会话级标志，不落盘），不要每次刷新又跳回去；
- 点"回今天"按钮同样关闭预览，直到下一个自然判定点（次日或本节下课后）再恢复。

**边界情况（容易漏的）**

| 情况 | 期望行为 |
| --- | --- |
| 早上 7:00 打开，第一节 8:00 | 显示**今天**（第三类，不预览） |
| 17:20 放学后 | 显示**明天**（或周一），标题标 `预览：` |
| 晚上 21:00 有晚自习 | lastEnd = 21:00，"上完"要到 21:15 之后才预览（自动正确，不用单独配置） |
| 今天下午全调空 | lastEnd 提前到上午最后一节，午后就预览 |
| 明天也放假（国庆） | 一直找到 10-08 才预览（15 天窗口内） |
| 周五放学后 | 预览**下周一**（跳过周六日） |
| 跨 00:00 | 新的一天重新判定；若新的一天有课 → 自动回到"今天" |
| 教室机长期不关机 | 每次判定按整分触发，不要在秒级重算（避免闪烁与 CPU 浪费） |

> 保留一个可选增强（不在本轮范围）：`预览开始时间`（如"只在 17:00 之后才允许预览"），
> 用于"课后服务到 18:30、但课表里没排"的班级。需要时再加。

## 4. 决策 D6 / D13（核心之二）：临时调整只在本周生效；原始课表可长期修改

### 4.1 现状问题：这两类是"永久生效"的

|  |  |  |
| --- | --- | --- |
`LessonOverride` 只有 `ClassName|DayIdx|Period`，**没有日期**。于是：

- 老师周三把第 3 节数学改成自习 → 这条记录**从本周一直生效到学期末**；
- 下周二一原课表该上数学，界面却还是自习；
- Excel 导入的临时课表同理，导一次就永久顶在那儿。

这和 §3 是同一枚硬币的两面：

| | 症状 | 本质 |
|---|---|---|
| §3 远程调代课 | 周末打开，本周调课**全没了** | 过滤**太狠**（基准用了"今天"） |
| §4 手工 / 导入 | 下周打开，上周的改动**还在** | 根本**没有过期机制** |

两个都要修，否则"本周课表对不对"还是不可信。

### 4.2 五层数据：原始课表 / 原始课表修改 / 导入 / 远程 / 手工

r6 起手工改课分成"改原始课表"和"改临时课表"两种，所以数据从"三类覆盖"变成**五层**：

| 层 | `Source` | 载体 | 生效区间 | 默认优先级 |
| --- | --- | --- | --- | --- |
| **L0 原始课表** | `base` | 分发/导入的 base 课表 | 永久（就是底表本身） | 底座（不可调） |
| **L1 原始课表修改** | `basePatch` | `basePatch.json` | **从修改起长期有效**（无 `ValidTo`） | 低 |
| **L2 电子表格导入** | `import` | 分发的 `import` 文件 | 用户选定的周 / 自定义区间 | 中 |
| **L3 远程同步（二一调代课）** | `remote` | 分发 `d/subs.json` 原始记录 | 服务端 `validStart~validEnd` | 高 |
| **L4 手工调整（临时）** | `manual` | `overrides.json` | 本周 / 自定义区间 | **最高** |

**默认优先级（可调，见 §5.4）**

```
manual（本周手工） > remote（远程调代课） > import（导入临时课表） > basePatch（原始课表修改） > base
```

**为什么 `basePatch` 排在 `import` 和 `remote` 下面**——这两条是设计要点，反直觉但重要：

1. **它只是"修正底表"，不是"这周的安排"**。老师把周三第 3 节永久改成自习，是本意上的底表修正；
   而教务发的"本周三第 3 节改物理"（remote）是**针对这一周的具体安排**，理应压过长期修改。
   否则会出现：教务发了调课通知，教室大屏却不认，仍显示老师自己改的自习。
2. **"临时"压过"长期"，是这类系统的通例**（Xibo、ClassIsland 的本地档案 vs 管理档案同理）。

> 但这一条**你可以改**：§5.4 的优先级是可拖动的。如果学校习惯是"我改的原始课表就是最终版"，
> 把 `basePatch` 拖到 `remote` 上面即可，代码不用动。

**五层不是五个文件，而是三条来源 + 两个本地层**

| 来源 | 产生方式 |
| --- | --- |
| 主机下发 | `base`（每班一份）、`import`（可选）、`subs`（全校远程调代） |
| 本机操作 | `basePatch`（周视图"原始课表"模式）、`manual`（悬浮窗 / 周视图"临时课表"模式） |

所以"数据源可选"是两层意思，别混（§5.4 详述）：

- **主机侧**：抓二一 / 收电子表格，可以只开一路，也可以两路都开；
- **教室机侧**：接收哪些层、层与层谁压谁。

### 4.3 数据模型：把"周"和"层"都写进记录

**r8 实际落地（`ScheduleCore/Models/LessonOverride.cs`）**

```csharp
public class LessonOverride
{
    public string ClassName { get; set; }
    public int DayIdx { get; set; }        // 0..6（日历星期：周一=0 … 周日=6）
    public int Period { get; set; }
    public string Subject, Teacher, Location, Note, Type;
    public bool IsEmpty { get; set; }      // 调空

    public string Source { get; set; }     // temp（导入 / 二一）| manual
    public DateOnly? ValidFrom { get; set; }   // 生效起（含）；null = 迁移前的旧记录
    public DateOnly? ValidTo   { get; set; }   // 生效止（含）
    public DateTime UpdatedAt { get; set; }

    [JsonIgnore] public bool HasRange => ValidFrom.HasValue && ValidTo.HasValue;
    [JsonIgnore] public bool IsActiveOn(DateTime date);   // 含首尾；无区间一律算生效（迁移兜底）

    // ★ 键必须带区间起点，否则"下周改同一格"会覆盖本周那条
    [JsonIgnore] public string Key     => $"{ClassName}|{DayIdx}|{Period}|{ValidFrom:yyyy-MM-dd}";
    // 同一日期内定位格子用三元组键（不含区间）
    [JsonIgnore] public string CellKey => $"{ClassName}|{DayIdx}|{Period}";
}
```

与设计稿的两处差异（都是实现层面的改良，语义不变）：

| 项 | 设计稿 | 实际实现 | 原因 |
| --- | --- | --- | --- |
| 区间类型 | `DateTime` | `DateOnly?` | 生效区间只到"天"，用 `DateOnly` 后 JSON 里是 `"2026-10-26"`，人眼可读；`null` 精确表示"迁移前的旧记录"，不需要 `DateTime.MinValue` 这种哨兵值 |
| `basePatch` 的"长期" | `ValidTo = DateTime.MaxValue` | 本轮不做 `basePatch`（§4.2 的 L1 层留到 P1b），故无此需求 | 见 §10 的 P1a 状态表 |

**为什么用两个键**：`Key` 带区间起点，用来"跨周共存"；`CellKey` 不带，用来"在**某一天**里定位这一格"。
`OverrideExpander` 内部全部用 `CellKey`，持久化 / 去重 / 判等用 `Key` —— 混用会写错（r8 修 bug 的主因之一）。

**`Key` 加 `ValidFrom` 是上一轮最容易踩的坑**：若 Key 仍是 `班级|星期|节次`，
老师本周改一次、下周再改同一格，**下周那条会直接覆盖本周那条**——本周的历史记录被"穿越修改"。

**`basePatch` 单独存一个文件**（不与 `overrides.json` 混）：

```jsonc
// basePatch.json —— 原始课表的本地修改，长期有效
{
  "schema": 1,
  "patches": [
    {
      "className": "七年级(1)班",
      "dayIdx": 2,                 // 周三
      "period": 3,
      "subject": "自习",
      "teacher": "",
      "location": "",
      "note": "原：数学 / 张老师",
      "baseSubjectAtPatch": "数学", // ★ 打补丁时底表是什么，用于冲突检测
      "updatedAt": "2026-10-31T15:20:00+08:00"
    }
  ]
}
```

`baseSubjectAtPatch` 是这一层最关键的一个字段：**它记住"我改的时候底表上是什么"**。
下次下发新 base 时，若该格底表已经变成别的东西（或该格消失了），就说明**二一那边也改了**，
必须提示冲突，而不是默默用旧补丁盖住新数据。

**优先级存设置里，不写死**

```csharp
// AppSettings
public List<string> SourcePriority = new()
    { "manual", "remote", "import", "basePatch" };   // 高 → 低；base 永远在最后
```

展开器**不允许**在代码里硬编码 `manual > import > remote`（旧实现就是这样），
一律读这个列表。否则用户拖了顺序，代码却按老顺序合并，界面上"优先级设置"就成了摆设。

### 4.4 手工改课：两个入口，改的层不一样（D13）

**入口与层位的对应关系（定稿）**

| 入口 | 改的层 | 生效范围 | 交互 |
| --- | --- | --- | --- |
| **悬浮课表**（大屏/浮动窗）双击格子 | `manual`（临时层） | **固定本周，不弹选择** | 直接改完即生效，最快 |
| **控制面板 → 周课表视图** 双击格子 | 弹选择：**原始课表 / 临时课表（默认）** | 原始=长期；临时=本周 / 自定义 | 多一步选择，为"深思熟虑的修改" |

设计意图很清楚：**在教室里看见课不对，随手改 → 只管这一周**（不会悄悄改掉整学期的底表）；
**坐下来在控制面板里整理课表 → 明确告诉软件"这是临时的还是永久的"**。

**临时课表模式（默认）：只剩两个选项**

```
生效范围： ( • ) 本周（11/01 – 11/07）
           (   ) 自定义日期…      [ 下周 ] [ 下两周 ] [ 手动选择 ]
```

- **删除「长期有效」**——要长期生效，就用「原始课表」模式，语义更准、也有冲突检测。
- 默认「本周」（按 §3.8 周起始日取窗口；默认周日 ~ 周六时，周日改课归入即将开始的新一周）。
- 底部回显：`本条仅在 11/01 – 11/07 的周三第 3 节生效，过期自动失效`。

**原始课表模式：长期有效，但要带三条护栏**

选中后：

```
[ 原始课表 ] 将修改本班基础课表，从今以后一直生效，直到你再次修改或恢复原值。
            不会改动二一排课系统里的数据。
             [ 继续 ]  [ 取消 ]
```

写入 `basePatch`（§4.3），视觉与撤销：

| 项 | 做法 |
| --- | --- |
| 视觉标记 | 该格左上角加**小三角/小点**，鼠标悬停显示 `原始课表已修改（10-31），原：数学 / 张老师` |
| 撤销 | 右键菜单 `恢复原值`（删掉这条 patch，立刻回到 base） |
| 汇总入口 | 调代课管理页新增分区 **`原始课表修改（N 条）`**，可逐条恢复或整体恢复 |
| 跨学期 | 新学期开学若 base 全量变化，提示 `检测到 8 条原始课表修改可能已失效，是否清空？` |

**★ 必须提醒的一条语义边界**

「改原始课表」**只改本机显示的底表，不会回写二一排课系统**。所以：

- 本机看是对的，二一后台、家长端、其他班看到的还是原样；
- 下次主机下发新 base 时，若同一格二一也改过 → 触发**冲突提示**（见下）。

如果希望真正改到二一，得反过来做（我们的程序去写二一），这不在本项目范围内，也不建议做。

**下发/重新导入 base 时，`basePatch` 怎么办（最容易出错的地方）**

| 场景 | 行为 |
| --- | --- |
| 新 base 该格**没变**（仍等于 `baseSubjectAtPatch`） | 补丁继续生效，静默 |
| 新 base 该格**变了**（二一也改了） | 补丁仍生效，但标 `冲突`：`下发版本：物理 / 李老师`，给 `采用下发版本` / `保留我的修改` 两个按钮 |
| 新 base 该格**没了**（课被删/调空） | 同上，标冲突（补丁还在显示旧科目，很可能是过时数据） |
| 新 base 整体是**新学期**（`termStart` 变了） | 主动提示 `是否清空全部 N 条原始课表修改`（默认不清，但必须提醒） |

> 为什么默认"补丁仍生效"而不是"下发优先"：老师改了原始课表却在下发后悄悄失效，
> 比"提示一次冲突"糟糕得多。宁可多一次提示，不可静默回退。

**悬浮窗改完给一句轻提示（可选，建议做）**

悬浮窗改完，底部短暂提示：`已改本周（临时）。要长期这样改？到控制面板周视图选「原始课表」`。
一行字，能省掉"为什么下周又变回去了"的疑问。

### 4.5 导入临时课表：只打补丁，绝不换底表（r7 修正）

#### 4.5.1 先说改掉的错误做法

**旧实现（要废弃）**：`BtnImportTemp_Click` 调 `ScheduleImporter.ImportTempSchedule`，
把整份临时课表的“干净科目”（剥掉 `(调)(代)`）**当作新底表写进 `schedule.json`**，
再额外把带标记的格子生成 `Source="temp"` 的覆盖记录。

这等于**用补丁文件换掉了底表**，后果有三层：

| 后果 | 具体表现 |
| --- | --- |
| **换掉底表** | 临时课表只含某一个年级（标题就写着“（八年级）”），一导入，另外两个年级 60 个班在运行数据里**直接消失** |
| **底表被污染** | 想回到“原始课表”只能重新导入总课表；中间的手工修改虽然保留，但底表已变，`Key` 对得上、语义已错 |
| **与五层模型冲突** | §4.2 里 `base` 与 `import` 是两个不同的层，旧实现把 `import` 写成了 `base`，层位概念直接失效 |

**r7 定稿：临时课表导入 = 只产生覆盖记录（`Source` 走 `import` 层语义），`schedule.json` 一个字节都不动。**

#### 4.5.2 新实现的正确性依据（实测）

对两份真实文件逐格比对（八年级：临时 1140 格 / 总课表 1200 格）：

| 比对结果 | 数量 | 说明 |
| --- | --- | --- |
| 带 `(调)/(代)` 标记 | **39**（32 调 + 7 代） | 这些才是“补丁”，正是要生成覆盖的部分 |
| 无标记且科目与总课表**完全一致** | 1106 | 没有任何信息需要写回底表 |
| 无标记但科目**不同** | **0** | ★ 关键：只取标记格**不会丢任何科目改动** |
| 临时课表有、总课表没有 | 0 | 不存在“凭空多出来的课” |
| 总课表有、临时课表**空白** | **60** | ★ 见 §4.5.4，唯一需要单独讨论的一类 |

七年级同样验证：标记 206 条，无标记差异 0 处，空白 2 处。

结论：**“只取标记格”在数据上成立**，旧实现“整份替换”纯属多余，还带来上面那三层损伤。

#### 4.5.3 导入流程（r8）

```
1. 选文件
2. 前置检查：当前没有底表 → 直接拒绝
   「请先导入全校总课程表（或改用二一缓存）再导入临时课表——临时课表只产生调代覆盖，不提供基础课表。」
3. 问生效区间（EffectiveRangeWindow）：本周 / 下周 / 下两周 / 自定义
4. 解析：只取 带(调)/(代) 标记的格子 → List<LessonOverride>（每条带 ValidFrom/ValidTo）
5. 班级校验：
   - 临时文件的班级名与底表「一个都对不上」→ 判定为选错年级，取消导入，什么都不写
   - 部分对不上 → 正常导入，但在状态栏点名这些不会生效的班级
6. 合并（★ 只替换「本次区间内」的导入记录）：
   overrides.RemoveAll(x => x.Source == "temp" && x.OverlapsRange(本次起, 本次止));
   overrides.AddRange(新记录); SaveOverrides
7. 重算刷新（AppEvents.RaiseScheduleChanged）
```

> 第 6 步的 `OverlapsRange` 是 r8 与 r7 的关键差异：r7 是 `RemoveAll(Source == "temp")` **一刀切**，
> 会把上一次为"下周"导的临时课表一起清掉。现在只清与本次区间重叠的那部分，**下周的记录还在**。
> ⚠️ 但 `Source` 目前只有一个 `temp`，二一的远程调代课也用这个值，所以"区间重叠 + temp"仍会误删远程记录 —— 见 §11.2。

**全程不调用 `Store.SaveSchedule`，不改 `ScheduleSource`，不重建教师课表。**
（旧实现顺带做了这三件事，现在都不需要——底表没变，教师课表自然不用重算。）

#### 4.5.4 临时课表“空白格”怎么处理（r8 定稿：不算调空，选 B）

八年级有 **60 格是「总课表有课、临时课表空白」**，且分布极规整：

```
周二 第8节  30 个班全空（总课表里是「自习」）
周五 第8节  30 个班全空（总课表里是「教师会议」）
```

r7 只改“不换底表”这一件事，**没有**为这些空白格生成“调空”覆盖。所以改造后：

| | 旧行为（换底表） | r7 新行为 |
| --- | --- | --- |
| 周二/周五第8节 | 显示**空白**（因为底表被换成临时课表） | 显示底表的 **自习 / 教师会议** |

两种解读都有可能，必须由你判断：

- **A. 空白 = 这些课被取消了**（学生周二第8节自习不上了、周五教师会议学生放学）
  → 需要为这些格子生成 `IsEmpty = true` 的覆盖（`LessonOverride.IsEmpty` 字段本来就有，渲染侧也已支持）。
- **B. 空白 = 教务做临时课表时懒得填那两节**（它们不属于“调代课”范畴）
  → 保持 r7 现状，显示底表的自习/教师会议，才是对的。

**定稿（r8）：选 B —— 保持现状，显示底表的「自习 / 教师会议」。**

理由：`自习` 和 `教师会议` 都是**非教学班编制内**的安排，做临时课表的人通常只填正课；
且 30 个班整齐一致的空，不像“逐个取消”，更像“整列没填”。

**因此代码里不为空白格生成 `IsEmpty` 覆盖**：改造后周二 / 周五第 8 节显示的是底表的自习与教师会议。
这条**随时可翻**：将来若教务确认“确实取消了”，只需在 `ImportTempOverrides` 里加一条
“底表有课、临时空白 → 生成 `IsEmpty=true` 覆盖”的规则（`LessonOverride.IsEmpty` 与渲染侧都已支持，改动 10 行以内）。

#### 4.5.5 生效周（沿用 r6 定稿，两选项）

导入时弹窗必须问，选项与 §4.4 的临时层一致（**r6 起已删除“长期有效”**）：

```
这份临时课表适用于： ( • ) 本周（11/01 – 11/07）
                    (   ) 自定义日期…   [ 下周 ] [ 下两周 ] [ 手动选择 ]
```

- 默认本周；若是“下周的临时课表”，走「自定义 → 下周」快捷按钮。
- 若 xlsx 里能识别出日期（表头或约定单元格），自动填入并提示 `已从文件识别到 11/02 – 11/06`。
- 我们的两份总课表是**快照、本身没有日期**，所以这一步必须问、不能猜。
- **一次导入 = 一个连续区间**（不拆多段）；要覆盖不连续的周，导两次。

**r8 已落地**：导入时会弹出 `EffectiveRangeWindow`（“这份临时课表从哪天到哪天生效？”），
四个快捷项 —— **本周（默认）/ 下周 / 下两周 / 自定义（起止日历选择）**，
选定的区间写进每条记录的 `ValidFrom/ValidTo`；状态栏回显
`调课 32 条、代课 7 条，生效期 10月26日 – 11月1日（过期自动失效）`。

> 边界提醒：`本周` 按 §3.8 当前实现是**周一起算**，所以周末（10/31 周六）导入“本周”，区间是 10/26–11/01，
> **11/02 周一起自动失效**。周六晚上要备下周的课，请选「下周」。
> 等“周起始日可配（默认周日）”落地后，这个坑会自然消失。

#### 4.5.6 导入后的替换范围

- **只替换 `import` / `temp` 这一层**（先清旧、再写新）。
- **不动 `remote`**：远程调代课本来优先级更高，删了下次轮询又回来，纯属自找麻烦。
- `manual`、`basePatch` 一律保留。
- 冲突时给提示：`该格已有手工修改（本周），已保留手工版本` /
  `本周三第 3 节有教务调课（远程优先），导入结果在该格不显示`。

#### 4.5.7 顺带修的同类问题：单班导入不再替换整份底表（r8）

**旧行为**：`BtnImportSingle_Click` → `ImportSingleClass` → `ApplyImportedSchedule` → `SaveSchedule`，
即“用一份单班课表整份覆盖 `schedule.json`”。一台机器上只要有人点一次“导入单个班级课表”，
其余几十个班在运行数据里**就全没了** —— 和 r7 修掉的临时课表问题是同一个病。

**r8 改为按班合并**：

```
新 = 旧底表（若有）
for 每份导入的班：新.Classes.RemoveAll(x => x.ClassName == 该班); 新.Classes.Add(该班)
→ ApplyImportedSchedule(新)
```

| 场景 | 行为 |
| --- | --- |
| 没有底表 | 直接新建（单班独立使用的场景不受影响） |
| 有底表 | 只替换同名班，其余班原样保留 |
| 状态栏 | `已合并到现有课表（原有 90 个班，现共 90 个班）` —— 一眼能看出有没有误删 |
| 选中班级 | 指向**刚导入的那个班**（旧代码指向 `ClassNames[0]`，合并后可能指向别的班，等于没切过去） |

> 仍未做：`ApplyImportedSchedule` 会把 `ScheduleSource` 改成 `"Excel"`。这是旧逻辑（防止下次启动被二一缓存覆盖回去），
> 在“合并”语义下不一定合适，留待 P1b 的“数据源与优先级”一起改（见 §5.4）。

### 4.6 过期之后怎么办：不删除，只失效

**保留记录、只是不参与渲染。** 理由：老师要能回看"上周那次调课是怎么改的"，也要能"把上周的改法沿用到本周"。

| 状态 | 界面表现 |
|---|---|
| 区间覆盖显示日 | 正常显示，带 `手工` / `导入` 小标记 |
| 区间已过 | 不参与渲染；在"调代课管理"列表灰显 `已过期（10/26–11/01）` + `续到本周` 按钮 |
| 区间在未来 | 灰显 `未生效（11/02 起）`，可提前取消 |
| **`basePatch`（原始课表修改）** | **不适用"过期"概念**——它没有 `ValidTo`，永远生效；单独分区管理，只能"恢复原值" |

> r6 起临时层（`manual`）**不再有"长期有效"选项**，所以"永久残留"的风险只剩 `basePatch` 一处，
> 而 `basePatch` 有视觉标记 + 冲突检测 + 一键恢复，比原来可控得多。

**清理策略（定稿：25 周）**：保留最近 **25 周**，更早的移到归档文件，避免 `overrides.json` 无限增长。

选 25 周的理由：**一个学期约 20–21 个教学周**，25 周足以覆盖"整学期任意一天都能回看"，且不会跨到下学期。

| 时点 | 记录状态 |
| --- | --- |
| 学期内任意时刻 | 本学期所有调代课**全部可回看**，一条都不会被折叠 |
| 学期结束后 ~3 周 | 仍在活动文件里（学期末盘点、家长会核对都方便） |
| 超过 25 周 | 移到 `overrides-archive-<学年学期>.json`，**只移不删** |

> ⚠️ 归档判断必须用 **`ValidTo` 已过期 25 周**，不能用"记录创建时间"——
> 一条 9 月创建、`ValidTo` 在 1 月的记录，按创建时间早该归档了，但它其实还有效。
> 另外 **`basePatch`（原始课表修改）不参与归档**——它不是"某一周的记录"，而是底表的一部分，
> 归档走"恢复原值"，不走"过期折叠"。

### 4.7 换周时的体验（必做，否则老师以为数据丢了）

周一早上打开，上周手工改的都不显示了（**这是正确的**，但反直觉）。必须给提示：

**方案 1（基础，必做）**——调代课管理页顶部横幅：
> `上周有 3 条手工调代课已过期，是否沿用到本周？ [全部沿用] [逐条选择]`

**方案 2（可选，防呆）**——改课窗口顶部灰字：
> `上周这格也改过（数学→自习），已于 11/01 过期`

建议先做方案 1，成本低、效果直接。

### 4.8 现有数据的迁移（定稿：按推荐方案，D16）

旧 `overrides.json` 没有 `ValidFrom/ValidTo`，也没有层位概念。定稿策略：

| 情况 | 处理 |
| --- | --- |
| 有 `UpdatedAt` | 归入 `UpdatedAt` 所在周（按**周一**起算，避免迁移逻辑依赖用户设置） |
| 无 `UpdatedAt` | 归入**当前周**，并写日志 |
| 全部旧记录 | `Source = manual`（旧数据本来就是"界面手工改的"，语义不变） |
| 一律 | ❌ **绝不设成"长期有效"/`basePatch`**——那等于把旧坑永久化 |

**★ 定稿：迁移后必给一次性提示（这是推荐方案的关键一步）**

因为旧记录按 `UpdatedAt` 归周，**很可能一条都不落在当前周**，升级当天老师打开会看到
"我改的调代课全没了"——技术上正确，体感上是数据丢失。所以迁移完成后弹一次：

```
检测到 27 条历史调代课（升级前未区分周次）。
其中 5 条属于本周，22 条属于已过去的周次（仍可在调代课管理里回看）。
[ 全部归入本周（22 条） ]   [ 保持原样 ]
```

- 选「全部归入本周」→ 把这 22 条的 `ValidFrom/ValidTo` 改写为当前周窗口，**一次性**；
- 选「保持原样」→ 不显示，但管理页能看到并逐条 `续到本周`；
- 无论选哪个，都**写日志 + 记 `migratedAt`**，此提示**只出一次**（`schemaVersion` 保证）。

**迁移的其它约定**

- 迁移**只做一次**（`AppSettings.OverridesSchemaVersion`），迁移前备份 `overrides.json.bak`（走 §4.11 的备份目录）；
- 迁移是**纯本地、幂等**的：重复执行不会二次改写；
- **不要迁移成 `basePatch`**：旧数据没有 `baseSubjectAtPatch`，做不了冲突检测，进了长期层就再也说不清来源。

**r8 已实施的部分（`Store.MigrateOverrideRanges`，在 `LoadOverrides()` 里自愈）**

| 项 | 现状 |
| --- | --- |
| 归周规则 | ✅ 按 `UpdatedAt` 归入其所在周（周一起算）；没有 `UpdatedAt` 的归入当前周 |
| 触发方式 | ✅ 读到 `ValidFrom/ValidTo` 都为 `null` 的记录就补上并回写，**天然幂等**，不需要 `schemaVersion` 字段 |
| 脏数据 | ✅ 区间反了（`ValidTo < ValidFrom`）自动交换 |
| 迁移前备份 `overrides.json.bak` | ❌ 未做（属 P1c 的 `OverrideBackupService`） |
| 一次性提示“是否全部归入本周” | ❌ 未做。**这是升级当天最容易被当成“数据丢了”的一环**，见 §11.2 |

> 实测：现有 35 条 `temp` 记录的 `UpdatedAt` 都是 2026-10-31（今天），迁移后区间 = 10/26–11/01，
> 本周照常显示，11/02（周一）自然失效 —— 这正是设计想要的行为，**不需要也不应该再清零**。

### 4.9 一套展开器统管五层（"有效底表 + 按序叠加"）

`OverrideExpander` 是**唯一**计算"这一格最终显示什么"的地方。拆成两步：

**第一步：算"有效底表"（长期层，与周无关）**

```
EffectiveBase(className):
    board = clone(base[className])
    for p in basePatch[className]:          // 长期修改，无期限
        board[p.dayIdx][p.period] = p       // 直接盖在底表上
    return board
```

**第二步：按显示周展开临时层，从低到高依次叠加**

```
Expand(className, displayDate):
    weekStart = WeekHelper.WeekWindow(displayDate, WeekStartDay)   // ★ 默认周日
    board     = EffectiveBase(className)                            // 已含 basePatch

    foreach layer in 从低到高(读 AppSettings.SourcePriority 的反序):
        if 该层被禁用: continue
        foreach o in layer where o.ClassName == className:
            for i in 0..6:
                date = weekStart + i
                if date ∉ [o.ValidFrom, o.ValidTo]: continue
                dayIdx = 日历星期(date)      // ★ 周一=0…周日=6，不能用 i
                board[dayIdx][o.Period] = o  // 后写覆盖前写 → 高优先级自然胜出
    return board
```

**关键实现约定**

| 约定 | 理由 |
| --- | --- |
| **按"低→高"依次写入，后写覆盖前写** | 比"每格收集候选再比大小"简单，且不会漏层、不会漏"同级取最新"这种边界 |
| **优先级读 `AppSettings.SourcePriority`，不硬编码** | 否则界面上的优先级设置成了摆设（§4.3） |
| **`base` 永远不参与排序** | 它是底座，不是覆盖层；`basePatch` 已单独作为 L1 处理 |
| **`idempotent`：同层同格多条时取 `UpdatedAt` 最新** | 只发生在"删不掉旧记录"的异常情况，兜底用 |
| **周视图 / 桌面背面 / 悬浮窗 / 打印 全调这一个函数** | 只允许一个"该显示什么"的答案来源，避免四处各算一遍 |

**r8 已落地的部分：`ScheduleCore/Services/OverrideExpander.cs`**

| 方法 | 用途 |
| --- | --- |
| `CellKey(班, 星期, 节次)` | 三元组键，所有"某一天里定位这一格"的地方统一用它 |
| `MapForDate(all, 班, 日期)` | 该班在这一天生效的覆盖，按 `CellKey` 归并；同格多条取 `UpdatedAt` 最新 → 返回字典，`BoardBuilder` / `WeekBuilder` 直接用 |
| `ForDate(all, 班, 日期)` | 未归并的当日有效集合（"该日无底表、逐节列出"的分支用） |
| `ForCellInWeek(all, 班, 星期, 节次, 周起始)` | 该格与这一周有交集的记录 → **删除 / 改写时的唯一定位方式**（不再拼字符串比 Key） |
| `ForClassInWeek(all, 班, 周起始)` | 该班与这一周有交集的全部记录 → "清除本周"用 |

调用关系（已全部接上）：

```
悬浮课表 ScheduleWindow ┐
周视图   WeekBuilder    ├→ OverrideExpander.MapForDate(按日期求交) → 渲染
桌面背面 BackdropService┘   （教师视图先经 TeacherOverrideApplier，衍生记录继承来源区间）
```

**本轮没做的（P1b/P1c）**：五层按 `SourcePriority` 叠加、`basePatch` 层、`localSuppress` 屏蔽清单、
"同格同层多条取 `UpdatedAt` 最新"的完整优先级比较（现在只靠"手工记录总是最后写"这一近似）。

好处：五层共用同一套"按周展开 + 按优先级叠加"逻辑，
不会出现"手工的过期规则漏写了""导入没参与优先级"这类问题。
周视图（`WeekView`）也调同一个函数，只是 `displayDate` 传周内任意一天。

### 4.10 删除"每周一自动清零"机制（本轮新增，必须一起做）

**现状代码（已定位）**

| 位置 | 内容 |
|---|---|
| `ScheduleCore/Services/Store.cs:151-168` | `TryWeeklyOverrideReset()`：算出本周周一 → 若 `LastClearedMonday ≠ 本周周一`，就 `SaveOverrides(new List<LessonOverride>())` **全清**，并记录标记 |
| `ClassBulletinApp/App.xaml.cs:240` | 登录成功后调用 `Store.TryWeeklyOverrideReset()` |
| `ScheduleCore/Models/AppSettings.cs:26` | `LastClearedMonday`（上次清空的周一日期，用于"一周只清一次"） |

**为什么必须删**

旧机制是**时间驱动**：一到新的一周就全清。因为当时覆盖记录**没有日期**，不清就会永久残留——清零是"没有生效期"时的替代方案。

新机制是**数据驱动**：每条记录自带 `ValidFrom/ValidTo`，过期自然不显示。

两者并存会直接打架：

| 场景 | 旧机制造成的后果 |
|---|---|
| 周一清零后，教务当天又补了一条周一的代课 | 下周一清零时把它连同本周其他记录一起清掉 |
| 老师上周五手工排了本周三的代课 | 周一清零 → 手工记录**不可恢复地丢失** |
| 二一远程调课带跨两周区间（教研活动） | 被清零后第二周失效，课表回退成基础课表 |

更要紧的是：**清零是静默的**，用户收不到任何提示，只会发现"我改的调代课不见了"。

**删除清单**

| 对象 | 处理 |
|---|---|
| `Store.TryWeeklyOverrideReset()` 方法 | ❌ 整段删除 |
| `App.xaml.cs:240` 的调用 | ❌ 删除（同处 `LastUsername` 的逻辑保留） |
| `AppSettings.LastClearedMonday` 属性 | ❌ 删除。旧 `settings.json` 里的残留字段会被反序列化**自动忽略**（System.Text.Json 默认忽略未知成员），下次保存即消失 |
| `MainWindow` "清除全部临时调课"按钮 | ⚠️ **保留，但拆成四个**：`清除本周` / `清除本周·远程` / `清除本周·导入` / `清除本周·手工`，见下 |
| `WeekView` "清除全部调课"（按班级） | ⚠️ 保留，但**必须限定在显示周内**（见下"连带必须修的键"） |

**r8 执行状态**

| 对象 | 状态 |
| --- | --- |
| `Store.TryWeeklyOverrideReset()` | ✅ 已整段删除 |
| `App.xaml.cs` 里的调用 | ✅ 已删除（登录后只保留"记住用户名"） |
| `AppSettings.LastClearedMonday` | ✅ 已删除属性；旧 `settings.json` 里的残留字段被 `System.Text.Json` 自动忽略 |
| `WeekView` 的"清除全部调课" | ⚠️ 已改名为 **"清除本周调课"**，范围限定到当前显示周（不再跨周误删） |
| `MainWindow` 的"清除全部临时调课" | ⚠️ **仍是"全清"**，未拆成 §4.10 要求的四按钮 —— 属 P1c，见 §11.2 |

**"清除"按钮定稿：四个，全部限定在"显示周"内**

| 按钮 | 清除范围 | 默认可见 | 二次确认 |
| --- | --- | --- | --- |
| **清除本周**（主按钮） | 显示周内的**全部**来源（remote + import + manual） | ✅ | ✅ `将清除本周 3 条调代课（含 1 条手工），不可撤销` |
| 清除本周 · 远程 | 显示周内 `Source = remote` | 收在"高级" | 简单确认 |
| 清除本周 · 导入 | 显示周内 `Source = import` | 收在"高级" | 简单确认 |
| 清除本周 · 手工 | 显示周内 `Source = manual` | 收在"高级" | ✅ 加粗警告（手工记录不可重建） |

三条铁律：

1. **四个按钮一律只作用于"当前显示周"**——绝不提供"清除全部/清空所有"，
   那是旧机制的思路，删了清零又留一个"一键全清"，等于把坑换个入口。
2. **跨周记录只清"显示周覆盖到的那部分"**：一条 `11/01–11/15` 的远程调课，在 11/01–11/07 周里点"清除本周·远程"，
   正确做法是把它的 `ValidFrom` 推到 `11/08`（**截断**），而不是整条删除——否则 11/08 之后那两周的调课也被一起干掉了。
3. 清除后**立即重算**并回显：`已清除本周 3 条，其余 12 条不受影响`。
4. **「清除本周·远程」必须是"本地屏蔽清单"，不能只删本地展开结果**。
   远程调代课来自主机下发的 `d/subs.json`，**删了下次轮询又会回来**（首次部署更明显：刚清完，10 分钟后全恢复）。
   正确做法：写 `localSuppress.json`，记录 `(className, dayIdx, period, date)` 或 `(substituteId)`，
   在 `OverrideExpander` 展开时**排除被屏蔽项**，而不是改动本地缓存里的 subs。
   界面要能看到"本周已屏蔽 2 条远程调课"，并提供**恢复屏蔽**（老师清错了能撤销）。
   —— 这条是"下发 + 本地可覆盖"架构里最容易漏的一环，不做的话按钮看起来生效、十分钟后失效。
5. **`basePatch`（原始课表修改）不属于任何"清除本周"按钮**：
   它是长期层、没有"哪一周"的概念。要撤只能「恢复原值」或「整体恢复原始课表」，
   而且**绝不放在"清除本周"的确认框里一起列出来**——否则老师点清除本周，顺手把整学期的底表修改也清了。

**★ 连带必须修的键（不修会误删跨周记录）**

`Key` 加上 `ValidFrom` 之后，现有几处"按 Key 删除"的代码会失效或误删：

| 位置 | 现有写法 | 问题 |
|---|---|---|
| `LessonOverrideWindow.xaml.cs:104` | `x.Key == $"{className}\|{dayIdx}\|{period}"` | Key 已变，**永远匹配不上 → 删不掉** |
| `ScheduleWindow.xaml.cs:845` | `o.Key == key` | 同上 |
| `WeekView.xaml.cs:404` | `RemoveAll(o => o.ClassName==… && o.DayIdx==… && o.Period==…)` | **跨所有周删除** → 把其他周同一格的记录一起删了 |
| `WeekView.xaml.cs:459` | `o.Key == key` | 同第 1 条 |

**r8 执行状态：四处已全部改完**（统一改为"显示周 + 该格"定位，见 `OverrideExpander.ForCellInWeek`）

| 位置 | 现行写法 |
| --- | --- |
| `LessonOverrideWindow` 保存 / 清除 | 按「班 + 星期 + 节次 + 与本周有交集」定位；保存时若旧记录没有区间，一并补齐 |
| `ScheduleWindow.UpsertOverride`（拖动调课） | 只清「本周该格的手工记录」，其他周与远程 / 导入来源不动 |
| `WeekView.Upsert`（周视图拖动 / 右键） | 同上，区间取**当前显示的那一周**（`_monday`） |
| `WeekView.ClearCell` / `ClearAll` | 只删与显示周有交集的记录，状态栏回显 `已清除 10/26–11/01 这一周 …` |

顺带修掉的两个小 bug：

1. `LessonOverrideWindow` 保存时**不更新 `Source`**，导致手动改过的记录仍标着 `temp`，下次导入会被当成临时记录删掉；
2. 保存时**不清 `IsEmpty`**：原来是"调空"的格子，填上科目后仍被当成空课。现在按"科目为空 = 调空"自动判定。

统一改法：删除时用「**显示周 + 该格**」定位 —— 先把候选按 §4.9 展开到显示周，拿到确定的
`(className, dayIdx, period, validFrom)` 再删，不要用拼接字符串比。

**降级风险（旧版会清空数据）与兜底**

删除清零逻辑后，回退旧版本仍然危险：旧版首次启动就执行 `TryWeeklyOverrideReset()`，
找不到匹配的 `LastClearedMonday`，会把新版积累的调代课**全部清空**。

> 无法用"写一个未来日期当哨兵"来预防——旧代码只和"本周周一"比较，写任何值都挡不住。

**定稿：加"版本回退自动备份"兜底（D11），详见 §4.11。** 它把"依赖人记得备份"变成"程序每次启动都自动备份"，
即使真的回退了、被清空了，也能一键恢复。发布说明仍然要写"不建议回退"，但不再依赖这句话生效。

**数据量增长与归档（定稿：25 周）**

不再清零后，`overrides.json` 会持续累积。按 §4.6 的 **25 周归档**处理：

- 超过 25 周的记录**移到** `overrides-archive-<学年学期>.json`（如 `overrides-archive-2026-1.json`），不直接删；
- 归档只影响"回看"，不影响任何一周的渲染；
- **`长期有效` 的记录永不归档**（见 §4.11 护栏）；
- 量级很小（手工覆盖单班一学期几十条，约几十 KB），归档文件不会大。

**新旧语义对照**

| 维度 | 旧机制（每周清零） | 新机制（生效期） |
|---|---|---|
| 触发方式 | 时间（每周一首次登录） | 数据（`ValidFrom/ValidTo` 与显示周求交） |
| 用户感知 | 静默消失 | 管理页灰显"已过期" + 可**续到本周** |
| 可恢复 | ❌ 不可 | ✅ 记录仍在，可续用 |
| 本周已过期的记录 | 被清掉 | 不显示，但保留 |
| 跨两周的记录 | 第二周失效 | 正常生效 |

### 4.11 版本回退自动备份（定稿：D11）

**要解决的问题**

删掉清零逻辑后，**回退旧版本 = 旧版启动即清空全部调代课**（§4.10）。
只靠"发布说明里写不要回退"是靠不住的——半年后忘了、或别人帮忙装错版本，数据就没了。

**机制：不是"备份功能"，而是"启动即备份 + 异常骤减可恢复"**

| 环节 | 做法 |
| --- | --- |
| 备份时机 | **每次启动、加载 `overrides.json` 之后、任何写操作之前**立即备份一份 |
| 文件名 | `backups/overrides-<yyyyMMdd-HHmm>-v<版本号>.json`，例如 `overrides-20261031-1120-v1.2.3.json` |
| 存放 | `%AppData%\ClassBulletinApp\backups\`（**不进分发目录、不进共享文件夹**，避免被下发的空文件覆盖） |
| 去重 | 同一小时内且内容 SHA-256 相同 → 不重复写（避免频繁重启刷出一堆重复文件） |
| 保留 | 滚动保留 **10 份**，超出删最旧（单份几十 KB，总量 < 1MB） |
| 版本标记 | `AppSettings.LastRunVersion` 每次启动更新，用于识别"当前版本 < 上次运行版本" |

**恢复触发条件（关键，避免误报）**

启动时**同时满足**以下三条才弹恢复提示，否则静默：

```
① 当前 overrides.json 条数 == 0（或比最近备份少 90% 以上）
② 最近一份备份非空，且时间在 7 天内
③ AppSettings.LastClearedAt 不在最近 10 分钟内（用户刚手动清除 → 属正常）
```

提示内容：

```
检测到调代课记录异常减少（37 条 → 0 条）。
可能是回退到了旧版本，旧版会在启动时清空调代课。
最近备份：10-31 11:20（v1.2.3，37 条）
[ 恢复这份备份 ]  [ 忽略 ]
```

**为什么是"条数骤减"而不是"版本号变小"**

版本号变小只能说明装了旧版，**真正丢数据发生在旧版运行期间**；而等用户装回新版时，版本号已经"变大"了。
所以**看数据本身的变化**才可靠——`0 条` 就是最典型的清零特征。

**恢复动作**

- 从备份还原到 `overrides.json`（先把自己当前的空文件再备一份 `overrides-before-restore-*.json`，可反悔）；
- 还原后按 §4.8 的迁移规则补 `ValidFrom/ValidTo`（备份可能来自旧 schema）；
- 还原后**立即重算**并提示 `已恢复 37 条，其中 12 条在本周生效`。

**「长期有效」记录的护栏（与 §4.6 归档联动）**

- 归档判断只看 `ValidTo` 是否已过期 25 周 → **`ValidTo` 远期（如 9999-12-31）的记录永不归档**；
- 但"永久覆盖"本身有风险，所以管理页给一个独立分区：`长期有效（2 条）`，可一键 `转为本周`。

**副作用与成本**

| 项 | 评估 |
| --- | --- |
| 启动耗时 | 多一次几十 KB 的文件复制，可忽略（异步执行，不阻塞窗口显示） |
| 磁盘 | 保留 10 份 < 1MB |
| 误报风险 | 用"骤减 + 时间窗 + 手动清除白名单"三重条件压到很低 |
| 代码量 | 一个 `OverrideBackupService`（约 100 行）+ 启动钩子 + 一个提示条 |

## 5. 数据源双路（D3）

### 5.1 两路共用一个"中间层"

不管数据从哪来，**必须先归一成同一份结构**，下游（分发、渲染）只认这一种。否则每加一个数据源就要改一遍渲染。

```
[源 A] 二一 API ──┐
                  ├→ 归一器 → NormalizedBoard { classKey, className, grade, lessons[], subs[], term }
[源 B] xlsx 表格 ─┘
```

**归一器输出（每班一份 `d/<classKey>.json` + 全校一份 `d/subs.json`）**：

```json
{
  "classKey": "g7-01",
  "className": "七年级(1)班",
  "grade": "七年级",
  "termStart": "2026-09-01",
  "lessons": [
    { "day": 0, "period": 1, "subject": "语文", "teacher": "张三",
      "room": "", "week": 0, "timeRange": "08:00-08:40" }
  ]
}
```

### 5.2 源 A：二一主机抓取

| 项 | 设计 |
|---|---|
| 位置 | 一台常开主机（办公室/家里均可） |
| 凭证 | **一个专用账号**（建议向教务申请"只读/信息员"账号），不是某个班主任的个人账号 |
| 凭证存储 | Windows DPAPI（`ProtectedData`，当前用户作用域），**不写明文** |
| token 维护 | `client-access-token` JWT 约 8 小时过期 → **每次抓取前先登录换 token**，不缓存长 token；登录失败才用旧 token 重试一次 |
| 抓取频率 | 每 30–60 分钟全量一次（数据量 8MB 级）；**新旧产物 SHA-256 相同则不动分发文件** |
| 抓取失败 | 保留上次产物 + `status.json` 标记 `ok=false`，**绝不产出空课表** |
| 产出 | 归一后的 `d/*.json` + 每班清单 `m/*.json` |
| 附加 | 同时导出 CSES（§2），作为备份与互通 |

**关键：`subs` 每次全量重抓。** 该接口忽略日期参数、返回全部历史（4070 条），"增量"没意义，整包覆盖最简单也最不易出错。

### 5.3 源 B：电子表格（网盘 / 共享文件夹）

| 形态 | 做法 | 适用 |
|---|---|---|
| **B-1 共享文件夹（UNC）** | 教务把导出的 xlsx 放到 `\\HOST\课表\`；主机（或每台教室机）直接读文件 | 局域网内，**最稳、零服务、零配置** |
| **B-2 网盘 WebDAV** | 教务上传到坚果云等；主机用 WebDAV 拉下来再转换为 JSON | 教务在异地、无常开主机 |
| **B-3 教室机直读 xlsx** | 教室机直接从 UNC/WebDAV 拉 xlsx → 用现有 `ScheduleImporter` 解析 | 无常开主机时的降级形态 |

**B 路的关键约束**：**xlsx 里没有"生效日期"字段**（我们的两份总课表是"某一版快照"，不是"带区间的调代课"）。
所以走 B 路时：

- 只能表达"**这一版课表长什么样**"，无法表达"这条调课只在这周生效"；
- 本质是 **"人工把当前有效状态固化下来"**——过期与否取决于**教务有没有及时导出新表**；
- 建议 B 路提供一个 `effectiveFrom` 字段（写在工作表约定单元格，或写进清单），客户端据此判断"这份表是不是本周的"，避免拿上个月的表当本周用。
- **注意区分**：B 路导入到教室机后，产出的覆盖同样是 `import` 类，同样按 §4 的规则**只在本周生效**——
  这样即便教务漏更新，最坏结果是"本周课表退回基础课表"，而不是"上周的临时表一直顶着"。

> **一句话差别**：A 路（二一）能自动区分过期；B 路（xlsx）不能，只能靠人口及时更新 + `effectiveFrom` 标记。

### 5.4 数据源可选 + 优先级可调（D14）

"可选 + 优先级"其实有**两个战场**，必须分开做，否则会互相打架：

| 战场 | 在哪设置 | 可选项 | 默认 |
| --- | --- | --- | --- |
| **主机侧：取哪几路数据** | 主机 puller 配置 | 二一 API / 电子表格 | **全选** |
| **教室机侧：接收哪些层、谁压谁** | 显示设置 →「数据源与优先级」 | `manual` / `remote` / `import` / `basePatch` | **全开**，顺序 `手动 > 远程 > 导入 > 原始课表修改` |

**★ 术语要统一（避免以后吵不清）**

- **数据源** = "数据从哪个系统来"（二一 / 电子表格）→ **只在主机侧选**；
- **层** = "教室机上按什么规则叠加"（五层，§4.2）→ **在教室机侧排序**。

教室机**不做"数据源"选择**——它拿到的是主机合并后的产物，不知道自己吃的是二一还是 xlsx。
这条原则不能破：一旦终端开始"选系统"，30 台就会各自不同步。

**教室机侧：设置界面长什么样**

```
数据源与优先级                      [ 恢复默认 ]
  ☑ 手动调整（本周）        优先级 1  ↑ ↓   ← 不可关闭，只能改次序
  ☑ 远程同步（二一调代课）  优先级 2  ↑ ↓
  ☑ 电子表格导入（临时课表）优先级 3  ↑ ↓
  ☑ 原始课表修改（长期）    优先级 4  ↑ ↓
  ──────────────────────────────────────
  原始课表（底表）                     固定最低，不参与排序
```

- 拖拽/上下箭头调整顺序，**改完立即重算并回显**：`本周三第 3 节现在显示：物理（远程优先）`；
- 每层的"来源说明"一行小字，避免老师不知道"远程同步"是什么：
  `远程同步：二一排课系统的调代课，按生效日期自动过期`；
- **`manual` 不可关闭**：关掉等于"我这周改的全不算"，风险太高。要清就按 §4.10 的按钮清；
- 每层可单独关闭（`☐`）：关掉 `remote` = 只显示原始+导入+手工，用于"我们班不跟二一调课"的极端情况。

**优先级冲突的可视化（很重要，否则设置项形同虚设）**

同一格被多层命中时，悬停显示：

```
周三 第3节   物理 / 李老师
  应用：远程同步（优先级2）
  被压制：手动调整(本周·数学)  ·  电子表格导入(数学)
```

老师能立刻看出"为什么我改的没生效"——九成疑问都出自这里。

**主机侧：两路都开时怎么合并**

| 场景 | 策略 |
| --- | --- |
| 两路都可用（默认） | **分层下发，不在主机合并**：二一出 `base` + `subs`；电子表格出 `import`。教室机按 §4.9 的优先级叠加 |
| 只开二一 | 只下发 `base` + `subs`，无 `import` |
| 只开电子表格 | 下发 `base`（来自表格）+ 可选 `import`（表格里若含调代课区块） |
| 两路打架（同一格） | **不在主机裁决**，交给教室机的优先级表——这正是"优先级可调"存在的意义 |

> **为什么改掉了 r5 的"主机合并成一份"**：既然你要"数据源可选 + 优先级可调"，
> 主机就必须**把层原样下发**，否则合并完再下发，教室机就没得选了。
> 代价是教室机多做一次叠加（很轻，几百条记录），换来的是"哪里不对就在本机调，不用改主机"。

### 5.5 预留排课软件开放接口（D15）

目的：现在靠抓网页接口（`client-access-token` + `/query/*`），**能用但属于"逆向"**——
对方一改版就坏。如果将来能和二一的老师谈成正式接口，我们希望**只改一个类**就能接上。

**接口抽象：所有数据源都实现同一个 `IScheduleProvider`**

```csharp
public interface IScheduleProvider
{
    string Id { get; }            // "eryi-web" | "eryi-open" | "excel" | "custom-http"
    string DisplayName { get; }   // 界面显示："二一排课（网页抓取）"
    Task<ProviderResult> FetchAsync(ProviderContext ctx, CancellationToken ct);
}

public record ProviderContext(string DataDir, string ClassKeyFilter, IProgress<string>? Log);
public record ProviderResult(bool Ok, List<NormalizedBoard> Boards, List<SubstituteRecord> Subs,
                            List<GradeTerm> Terms, string? Error, DateTime FetchedAt);
```

- 现在的 `ErYiClient` 抓取逻辑 → 包成 `ErYiWebProvider`（**不改内部实现，只加壳**）；
- 电子表格 → `ExcelProvider`；
- 未来二一开放 API → 新增 `ErYiOpenProvider`，**其余代码一行不动**；
- 其它厂商（正方/强智/自定义）→ `CustomHttpProvider`（见下）。

**`CustomHttpProvider`：给我们自己留的"万能插座"**

配置项：`Url` / `Method` / `Headers`（可放 Bearer）/ `Timeout` / `SchemaUrl`（可选）。
期望对方返回我们定义的 **`schedule-feed.schema.json`（v1）**，最小结构：

```json
{
  "schema": 1,
  "generatedAt": "2026-10-31T06:00:00+08:00",
  "termStart": "2026-09-01",
  "classes": [
    {
      "classKey": "g7-01", "className": "七年级(1)班", "grade": "七年级",
      "lessons": [
        { "day": 0, "period": 1, "subject": "语文", "teacher": "张三",
          "room": "", "week": 0, "start": "08:00", "end": "08:40" }
      ]
    }
  ],
  "substitutes": [
    { "className": "七年级(1)班", "srcSlot": 16, "destSlot": 16,
      "subject": "数学", "teacher": "李四",
      "validStart": "2026-10-26", "validEnd": "2026-10-30" }
  ]
}
```

字段语义必须写进规范文档（尤其 `week: 0/1/2` = 每周/单周/双周、`slot = day*8+period-1`），
否则接的人一定会理解错——这是接第三方最容易翻车的地方。

**★ 跟二一的老师沟通，要问清这 8 件事**

| # | 问题 | 为什么问 |
| --- | --- | --- |
| 1 | 有没有**正式开放 API**（文档 + 授权流程）？ | 决定我们是否继续走逆向 |
| 2 | 鉴权方式？`client-access-token` 有效期多久、能否**长期有效**或自动续期？ | 现在 7h53m 过期，主机必须定时重登 |
| 3 | 有没有**只读账号 / 学校级 token**（而非某位老师的个人账号）？ | 避免绑死个人、改密码就崩 |
| 4 | 调代课的 `validStartDate / validEndDate` 是否**稳定字段**？ | 我们整套"按周生效"都建在它上面 |
| 5 | 有没有**增量接口**（只拉变更，而不是每次 90 班全量 8MB）？ | 决定轮询频率和流量 |
| 6 | 有没有**变更通知 / webhook**？ | 有的话可以去掉轮询 |
| 7 | 单双周（`alternateWeek`）、固定项（大课间/眼保健操）有结构化字段吗？ | 现在靠 `commonSectionList` 推算 |
| 8 | **学校是否书面同意**我们用程序读取这些数据？ | 合规底线，也是对方愿不愿意配合的前提 |

> 第 8 条别跳过。哪怕数据是"本校自己的课表"，用程序批量抓取也需要学校知情同意；
> 将来出了争议，这一条比技术方案重要得多。

**落地节奏（不阻塞当前开发）**

- **现在**：把 `ErYiClient` 包成 `ErYiWebProvider`（半天工作量），接口先空着也能跑；
- **同时**：把 `schedule-feed.schema.json` + 字段说明写成一页纸，谈的时候直接给对方看；
- **谈成后**：新增 `ErYiOpenProvider`，在设置里切换数据源，A/B 对比两周再切正式。

## 6. 分发通道双方案（D4）

### 6.1 统一抽象：三种源，一套比对逻辑

```csharp
interface IFeedSource {
    string Name { get; }                       // "http" / "unc" / "webdav"
    Task<byte[]?> ReadManifestAsync(CancellationToken ct);
    Task<bool> DownloadAsync(string path, string destTmp, CancellationToken ct);
}
```

| 实现 | 地址形态 | 说明 |
|---|---|---|
| `LocalFeedSource` | `\\HOST\课表\` 或 `D:\课表共享\` | 共享文件夹。**最稳**：无服务、无端口、断外网也能用 |
| `HttpFeedSource` | `https://xxx.trycloudflare.com/` | Cloudflare Tunnel 暴露的主机 HTTP 目录 |
| `WebDavFeedSource` | `https://dav.jianguoyun.com/dav/课表/` | 坚果云等，用**应用密码** |

三者的**比对、下载、原子替换、降级逻辑完全一样**，只有"怎么读字节"不同。这是本设计的核心复用点。

### 6.2 通道 A：内网穿透（Cloudflare Tunnel）／ 共享文件夹

- **局域网内**：直接用 UNC 共享文件夹，**优先级最高、零依赖**。
- **异地/外网**：主机跑 `cloudflared` 隧道，教室机访问 `https://<域名>/m/g7-01.json`。
- 教室机**不需要装任何客户端**（优于 Tailscale 的 30 台装机量）。
- 前置验证：**校内网络能否稳定访问 Cloudflare**（A 案唯一的不确定性，必须先实测）。

**多源回退顺序（建议）**：

```
① UNC 共享（局域网，最快）
② Cloudflare Tunnel（外网可达）
③ 网盘 WebDAV（最后的兜底）
④ 本地缓存（离线仍可显示）
```

每级超时 3–5 秒；全部失败则用缓存 + 界面角落提示"数据可能不是最新（最后更新：xx）"。

### 6.3 通道 B：网盘 WebDAV

- **载体**：坚果云（`https://dav.jianguoyun.com/dav/`），用**应用密码**，不用账号密码。
- **必须做变更检测**：只拉 `m/<classKey>.json`（0.5KB）比对，不无脑下 8MB。
- **流量估算**（按班切分清单后）：0.5KB × 144 次/天 ≈ 72KB/天/台，30 台 ≈ **2.2MB/天 ≈ 65MB/月**，远低于坚果云免费额度。
  （对比：若不分班切清单，全校一张 18KB，则 78MB/天，会爆额度——这就是 §1.3 按班切分的直接理由。）
- 网盘适合**分发小文件**；若坚持走"直发 xlsx"形态（B-3），注意 xlsx 有几 MB，多点并发可能被限速。

## 7. 教室机客户端改造点（文件级清单）

> 仅列改动位置与性质，具体代码待确认后写。

| 文件 | 改动 | 性质 |

## 8. 主机端（puller）设计

一个控制台小工具 / 一个 PowerShell 脚本均可，逻辑固定：

```
每 N 分钟：
  1. 登录二一（专用账号）→ 拿 client-access-token
  2. 抓 project-list / grade-tree×3 / class-lectures×90 / substitute-list×3
  3. 归一 → 按班生成 d/<classKey>.json；全校生成 d/subs.json；每年级生成 d/term-g<7|8|9>.json
  4. 逐文件算 SHA-256，与上一次产物比较：
        无变化 → 只更新 m/*.json 的 generatedAt（或干脆不动）
        有变化 → 写新文件（先 .tmp 再替换），重算清单
  5. 写 m/<classKey>.json（每班一份）+ 可选 cses/<className>.cses.yaml
  6. 写 status.json：{ lastRun, ok, classCount, subCount, error }  ← 供排查
  7. 失败：保留上次全部产物，只更新 status.json 的 ok=false（**绝不删除 d/ 下的文件**）
```


**产物目录**：

```
feed/
├─ m/g7-01.json          ← 每班清单（教室机只拉这一个）
├─ d/g7-01.json          ← 每班基础课表
├─ d/subs.json           ← 全校调代课原始记录
├─ d/term-g7.json        ← 年级时间表 + 固定项
├─ cses/七年级(1)班.cses.yaml
└─ status.json
```

**部署形态**（任选，互不影响）：
- 裸目录 + `python -m http.server` → 配 Cloudflare Tunnel；
- 裸目录直接设共享 → 教室机走 UNC；
- 目录同步到网盘（坚果云本地文件夹）→ 教室机走 WebDAV。

## 9. 降级、安全与运维

### 9.1 降级阶梯（必须全部实现）

| 情况 | 行为 |
|---|---|
| 清单 404 / 超时 | 用本地缓存，指数退避，不弹窗打扰 |
| 单文件 SHA-256 不匹配 | 保留旧文件，本轮不更新，写日志 |
| 全部文件下载失败 | 回退 `last-good/` |
| 新数据解析失败 | **不切换**，继续用旧数据，界面标注"数据异常，显示的是 X 日数据" |
| 首次安装无缓存 | 显示"正在获取课表…"，失败则提示"请联系管理员"，**不显示空课表** |
| 覆盖区间全部过期 | 显示基础课表（这是正确结果，不是故障） |

### 9.2 安全

- 二一凭证：只存在于**主机**，DPAPI 加密；教室机**完全没有凭证**（相对"30 台各自登录"的最大优势）。
- 共享文件夹：只读权限给教室机账号，写权限只给主机。
- Cloudflare Tunnel：可加 Cloudflare Access（邮箱验证）或自定义随机路径；课表本身不高度敏感，但不必公开可爬。
- 网盘：应用密码独立于账号密码，可随时吊销。
- 日志里**不打印 token / 密码**。

### 9.3 观测性（给"看不见的 30 台机器"留个眼睛）

- `status.json` 记录主机侧最后一次成功时间、班级数、调代条数；
- 教室机界面小字显示"数据更新于 X 分钟前"；
- 超过 24 小时未更新 → 用醒目但仍克制的提示（不要弹窗）。
