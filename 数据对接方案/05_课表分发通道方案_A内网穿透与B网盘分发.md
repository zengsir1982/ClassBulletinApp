# 05 · 课表分发通道方案（A 内网穿透 / B 网盘分发）

> 目的：解决「**教务在任意联网电脑更新 → 教室机定时拉取 → 更新临时课表**」这条链路，
> 同时**打破"集控必须同一局域网"的限制**。
> 本文件只做方案展开与对比，**不涉及任何代码改动**，供决策后再实施。

---

## 0. 背景与诉求

| 现状 / 约束 | 说明 |
|---|---|
| 二一排课（源头） | 数据权威但**必须鉴权**（`client-access-token` JWT 约 8 小时过期），无免登录端点（实测全 404） |
| 腾讯文档 | 公开可读可导出、任意地点可编辑，但**单元格要经 protobuf + 防爬 token + 补充接口**才拿得到，解析脆弱 |
| 现有集控设计 | `manifest.json`（版本号）+ `{id}` 差异化 + 教室机轮询缓存 —— **机制本身很稳，只是分发点默认在局域网** |
| 核心诉求 | 编辑端在公网（任意电脑），消费端（30 台教室机）定时拉取；不希望被"必须同网段"绑死 |

**关键认知**：集控 ≠ 必须局域网。集控的本质是「**一个分发点 + 多个客户端拉取**」，
这个分发点放在**公网**上就是联网集控（ClassIsland 的静态文件模式本来就托管在 GitHub/Gitee）。
所以 A 案的思路是：**保留现有集控机制，只把它搬到公网可达的位置**。

---

## 1. 共同前提（A / B 都必须做到，与选型无关）

无论最后选哪条路，以下五条是**必须实现的安全底线**，否则教室机会出现空课表：

1. **本地缓存**：拉到的课表文件落本地，断网时照样能用。
2. **解析失败保底**：新文件解析失败时，**保留上一次的好数据**并在界面提示，绝不清空。
3. **变更检测**：先 `HEAD` / 取 `ETag` / `Last-Modified` / 文件大小，**变了才下载**，不要每次无脑下载。
4. **轮询间隔**：调代课是「一天几条」量级，**5–15 分钟**足够；实时推送收益不大、徒增复杂度。
5. **安全**：公网分发的文件**不要使用完全公开的直链**，至少加随机路径或简单 token；
   课表虽不高度敏感，但应避免被随意爬取。

> 现有 `Source="temp"`（远程下发）/ `Source="manual"`（本地手工覆盖）的分层已经正确：
> 远程源只替换 temp，本地手工调代课不受影响。

## 2. 方案 A：内网穿透 / 虚拟组网（打破局域网限制）

**思路完全不变**：一台"集控主机"负责取数 → 生成带版本号的静态文件 → 提供 HTTP；
教室机轮询 `manifest.json`。
A 案解决的只是「**这台主机怎么让教室机在任意网络下都能访问到**」。

### A1 · Cloudflare Tunnel（**优先推荐**）

主机上运行 `cloudflared`，它**主动向 Cloudflare 边缘建立出站连接**，
Cloudflare 分配一个公网 HTTPS 域名，外部访问 → 经隧道转发到本机 HTTP 服务。

- **优点**
  - **不需要公网 IP**、不需要路由器开端口、不需要备案；
  - HTTPS 自动，安全性好；免费额度对小文件完全够用；
  - **主机放哪都行**（办公室 / 家里 / 宿舍），教室机填一个 HTTPS 地址即可；
  - 教室机**不需要装任何额外客户端**。
- **缺点 / 风险**
  - 依赖 Cloudflare 可达；**国内访问 Cloudflare 的稳定性必须实测**（要重点验证）；
  - 免费随机域名（如 `xxx.trycloudflare.com`）重启可能变化 → 建议绑自己的域名（需一个域名 + Cloudflare 托管 DNS，成本很低）；
  - 仍需一台常开主机（这是所有"主机集控"方案的共性）。
- **部署概要**
  1. 主机装 `cloudflared`，登录并创建命名隧道；
  2. 隧道指向本机静态文件服务（如 `http://localhost:8080`，目录里放 `manifest.json` + 各班 JSON）；
  3. 教室机配置填 `https://<域名>/manifest.json`。

### A2 · Tailscale / ZeroTier（虚拟组网）

主机与 30 台教室机**都装客户端**，加入同一虚拟网络，各机分配虚拟内网 IP（如 `100.x.y.z`）。
教室机访问主机就像访问局域网：`http://100.x.y.z:8080/manifest.json`。

- **优点**
  - 主机异地也"像在同一网段"，**教室机代码里仍是内网地址，改动最小**；
  - 打洞成功时点对点直连，延迟低；Tailscale 免费版支持 100 台设备（30 台够用）。
- **缺点 / 风险**
  - **每台教室机都要装并登录客户端**（30 次运维量，这是最大成本）；
  - 打洞失败会走中转（DERP），速度下降；学校网络若封锁 UDP 会影响打洞（Tailscale 有 TCP 回退）；
  - 依赖第三方控制面（可自建 Headscale 完全自控，但更重）。

### A3 · frp（自建反向代理）

需要**一台有公网 IP 的云服务器**跑 `frps`，主机跑 `frpc` 把本机 HTTP 映射出去。

- **优点**：完全自控、不依赖第三方、速度取决于自己的云服务器。
- **缺点**：**要买云服务器**（几十元/月）+ 域名（可能需备案）+ 自己维护 frps。
- **适用**：已有云服务器，或不想依赖 Cloudflare / Tailscale。

### A 案三选一对比

| 维度 | A1 Cloudflare Tunnel | A2 Tailscale | A3 frp |
|---|---|---|---|
| 需要公网 IP | ❌ 不需要 | ❌ 不需要 | ✅ 需要（云服务器） |
| 教室机装客户端 | ❌ 不需要 | ✅ **需要（30 台）** | ❌ 不需要 |
| 依赖第三方 | Cloudflare | Tailscale 官方 | 无（自控） |
| 成本 | 免费（自定义域名另算） | 免费（100 台内） | 云服务器月费 |
| 运维量 | 低 | **中高（30 台装机）** | 中（维护 frps） |
| 国内可达性 | ⚠️ **需实测** | 较好（有中转） | 取决于云服务器 |
| 主机需常开 | ✅ | ✅ | ✅ |

### A 案对现有代码的影响：**极小**

- 教室机：把 `AppSettings` 里的分发地址从局域网地址改成公网 / 虚拟网地址即可；
  `manifest` / 版本号 / `{id}` / 轮询缓存逻辑**完全复用**。
- 主机端：不变（仍是生成静态文件 + 提供 HTTP）。
- 新增建议：配置**多源回退**——先试公网地址，失败回退局域网地址（或反之），隧道/网络异常时也不影响展示。

## 3. 方案 B：网盘 / WebDAV 分发

**核心思路**：教务在任意电脑编辑腾讯文档 → **导出 xlsx → 上传到网盘** →
教室机定时从网盘**直链下载 xlsx** → **用现有 Excel 导入器解析**。

**最大价值**：**不需要任何常开机器**，教务上传即生效；且复用现有 `ScheduleImporter`，几乎不用写新解析器。

### B1 · 坚果云 WebDAV（**推荐载体**）

坚果云开放标准 WebDAV（`https://dav.jianguoyun.com/dav/`），支持**应用密码**。

- **优点**：国内速度好；WebDAV 是标准协议，程序化拉取简单；
  免费额度（上传 1GB/月、下载 3GB/月）对"几十 KB 的 xlsx + 变更检测"来说**完全够用**；
  支持 `ETag` / `Last-Modified`，天然适合增量拉取。
- **注意**
  - **务必用"应用密码"**，不要直接用账号密码；建议统一用一个只读应用密码，或按机器分发。
  - 流量估算：若**不做变更检测**、30 台每分钟拉一次 ~50KB → 约 2GB/天，**会超额度**；
    做了 `ETag` 比对后，实际只有"文件变化那次"才下载，流量可忽略。
- **部署概要**
  1. 网盘里放一个 `课表.xlsx`（教务导出后覆盖上传）；
  2. 教室机配置 WebDAV 地址 + 应用密码 + 远程路径 + 本地缓存路径；
  3. 定时 `HEAD` 比对 `ETag`，变化则下载 → 调现有导入器 → 失败则保留上一版。

### B2 · 其他网盘评估

| 载体 | 程序化拉取可行性 | 结论 |
|---|---|---|
| OneDrive | 需 Graph API + OAuth，国内速度不稳 | 不推荐 |
| 腾讯微云 | API 基本不开放，同步客户端为主 | 难程序化，只能用 B3 同步形态 |
| 百度网盘 | 开放平台有 API，但**限速严重**、非会员体验差 | 不推荐 |

### B3 · 「网盘同步文件夹」形态（另一种做法）

教室机装网盘客户端（坚果云 / 微云 / OneDrive），把课表文件夹**同步到本地目录**，
App **只读本地同步目录的文件**（用现有 Excel 导入器）。

- **优点**：**App 完全不用写网络代码**，同步、断点续传、冲突处理都交给网盘客户端。
- **缺点**：**30 台都要装并登录网盘客户端**（运维量与 A2 相当）；同步延迟不可控（通常秒级到分钟级）。
- 这是"最省开发"的方案，但**运维量换到了装机上**。

### 数据格式：直发 xlsx，还是转 JSON？

| 选择 | 优点 | 代价 |
|---|---|---|
| **直接分发 xlsx（建议先做）** | 复用现有 `ScheduleImporter`（ClosedXML），教务导出即用，**零转换** | 每次要解析 xlsx（几十毫秒，无所谓）；依赖教务导出时选对文件 |
| 转成 JSON 再分发 | 解析更快、可带版本号、可做增量 | 多一个转换步骤（需要有人/有服务跑转换） |

> 建议：**先直发 xlsx** 跑通链路；后续若需要版本号 / 增量 / 回滚，再升级到 JSON + manifest。

### B 案对现有代码的影响：中等偏低

- 新增一种数据源类型 `WebDavSource`（配置：URL / 应用密码 / 远程路径 / 本地缓存路径）。
- **复用现有 `ScheduleImporter.Import(xlsxPath)`**，不需要新解析器。
- 轮询定时器可与集控的 manifest 轮询共用一套。
- 主要工作量：WebDAV 客户端 + 变更检测 + 失败降级。

## 4. A 与 B 对比 & 决策建议

| 维度 | A 内网穿透 | B 网盘分发 |
|---|---|---|
| 是否复用现有集控机制 | ✅ **完全复用**（manifest/版本/{id}） | ⚠️ 部分复用（轮询/降级可复用，数据格式是 xlsx） |
| 教室机改动 | **极小（换地址）** | 中等（新增 WebDAV 拉取 + 复用导入器） |
| 教务每次更新要做 | 改腾讯文档（可全自动） | 改腾讯文档 **+ 导出 xlsx + 上传**（两步人工） |
| 需要常开机器 | ✅ **需要** | ❌ 不需要 |
| 需要公网 IP / 域名 | Tunnel 不需要；frp 需要 | 不需要 |
| 教室机装客户端 | Tunnel 不需要；Tailscale 需要 | 直连不需要；同步形态需要 |
| 依赖第三方 | Cloudflare / Tailscale / 云服务器 | 坚果云等网盘 |
| 断网可用 | ✅ 本地缓存 | ✅ 本地缓存 |
| **最大风险** | 主机宕机 / 隧道或组网失效 | 网盘限速、API 变更、或漏做人工上传 |

### 决策树

```
能否安排一台常开的电脑（办公机 / 旧电脑 / 迷你主机）？
├─ 能 ──> 想要全自动、改动最小 ──> 【A1 Cloudflare Tunnel】★ 首选
│            （前提：先实测校内能否稳定访问 Cloudflare）
└─ 不能 ──> 教务能否接受「改完点一下导出 + 上传」？
             ├─ 能 ──> 【B1 坚果云 WebDAV 直连】★ 首选（零服务器）
             └─ 不能 ──> 需要全自动又无常开机器 ──> 走 D 案
                          （对象存储 + Serverless / GitHub Actions 定时生成）
```

### 组合方案（可选）

两者不互斥，可以**双源冗余**：

- **主源** = 网盘 xlsx（有人上传就最新，语义直观）；
- **备源** = 穿透后的集控主机（全自动生成，带版本号）；
- 教室机取**版本较新 / 时间较新**的一份，任一失败自动切另一份。

代价是客户端逻辑复杂一点，通常**二选一即可**，除非对可用性要求很高。

4. **能否接受给 30 台教室机装客户端？**（A2 / B3 的前提，运维量不小）
5. **教务能否接受"导出 xlsx + 上传网盘"这两步？**（B 案的前提）
6. **坚果云账号与应用密码由谁管理？**（B 案需要；建议专人保管、定期更换）

## 6. 结论速览

- **A 的价值**：把"必须局域网"变成"主机放哪都行"，**几乎不改教室机代码**，体验最好；代价是**要有一台常开主机**。
- **B 的价值**：**不需要任何常开机器**，上传即生效，复用现有 Excel 导入器；代价是**每次更新多两步人工**（导出 + 上传）。
- 若想"既要全自动、又不要常开机器"，那就必须引入云端（对象存储 + Serverless，或 GitHub Actions 定时跑），即之前提到的 **D 案**。
