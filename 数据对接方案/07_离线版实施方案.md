> 版本：r1（2026-10-31）
> 前置：`06_课表分发实施设计_校验和与本周生效.md` r8（生效区间、OverrideExpander、删清零）
> 本文只做方案，**不含代码改动**。确认后才进入实施。

## 0. 结论速览

| 问题 | 结论 |
| --- | --- |
| 程序能不能离线跑 | **本来就是离线的**：全库 0 处 `HttpClient`/`WebClient`，`ErYiClient` 只读本地 JSON 目录，`FetchLive` 还是 `NotImplementedException`，登录是本地单账号 |
| 学校 FTP 能不能用 | **能，而且比共享文件夹更省事**：只用一个固定文件名 `manifest.json` 做变更检测，不需要列目录、不需要中文文件名、零 NuGet 依赖 |
| 三个年级怎么合并 | 先修一个**必修 bug**（七年级每天 13 列，解析器按 12 列硬编码 → 每天丢第 8 节），再把导入改成"按班合并" |
| 长期改课（版本化底表） | **语义完全可行**，但不要真存第二份底表；用 `Source=basePatch` + `ValidTo=null`（开放区间）表达，改动量约为"真版本化"的 1/5 |
| 数据包为什么要分两类 | 不分类 = 把 302 班的作业和窗口位置拷给 303 班。见 §3 |

## 1. 现状核查（实测数据）

### 1.1 三份总课表的结构差异（关键）

| 年级 | 列数 | 每天列宽 | 星期列位置 | 每天节次 | 特殊列 |
| --- | --- | --- | --- | --- | --- |
| 七年级 | 66（A..BN） | **13 列** | 2, 15, 28, 41, 54 | 8 节 | 大课间 / 眼保健操×2 / **午休** / 空列 |
| 八年级 | 61（A..BI） | 12 列 | 2, 14, 26, 38, 50 | 8 节 | 大课间 / 眼保健操×2 / 空列 |
| 九年级 | 61（A..BI） | 12 列 | 2, 14, 26, 38, 50 | 8 节 | 同八年级 |

### 1.2 ★ 必修 bug：七年级每天丢第 8 节

`ScheduleImporter.ParseAllCore` 第 259 行：

```csharp
for (int off = 0; off < 12; off++) { int c = start + off; ... }   // ← 写死 12 列
```

七年级每天 13 列，用 12 列去读 → 每天最后一列（第 8 节）读不到。

**实测证据**（`ParserTest` 跑七年级总课表）：

```
=== 七年级(1)班 星期一 ===
  第1节 … 第7节 体育与健康 / 阮楠 操场        ← 只有 7 节，没有第 8 节
=== 八年级(1)班 星期一 ===
  第1节 … 第8节 班会 / 赵少兴                 ← 正常 8 节
```

而 Excel 里七年级(1)班周一的第 14 列确实是 `第8节 16:35-17:15  班会/覃杨英`。

**影响面**：七年级 30 个班 × 5 天 = **150 节课被静默丢弃**。不修就无法谈"合并三个年级"。

**修法**（3 行）：块宽改为由相邻星期列相减得到，不再写死 12。

```
width[i] = (i+1 < dayCols.Count ? dayCols[i+1] : lastCol+1) - dayCols[i]
// 七：15-2=13 … 66+1-54=13
// 八：14-2=12 … 61+1-50=12
```

### 1.3 另外两个已确认的事实

- `BtnImport_Click`（导入全校总课程表）→ `ApplyImportedSchedule` → `Store.SaveSchedule(sf)`：**整份替换，无合并**。导入顺序 七→八→九，最后只剩九年级 30 班。你机器上 `schedule.json` 现在正好 30 个班、全是八年级，就是这个原因。
- 运行数据目录（`%APPDATA%\ClassBulletinApp\`）共 7 个 JSON + 1 个 png：

| 文件 | 大小 | 内容 | 性质 |
| --- | --- | --- | --- |
| `schedule.json` | 334 KB | 底表（班级→星期→节次→课） | 公共 |
| `teacher_schedule.json` | 338 KB | 教师个人课表（由底表派生） | 公共·可重建 |
| `overrides.json` | 12 KB | 调代覆盖 35 条 | 公共·分层 |
| `notifications.json` | — | 通知公告 | 公共·可选 |
| `homework.json` | 545 B | 作业公示 | **本班私有** |
| `missing.json` | 126 B | 缺交名单 | **本班私有** |
| `settings.json` | 5.2 KB | 全部设置（账号/班级/布局/主题…） | **混合，必须拆** |
| `desktop_backdrop.png` | 2.4 MB | 生成的桌面背景 | 派生·可重建 |

## 2. 学校 FTP 怎么做（可行，且推荐）

### 2.1 结论

**可行，而且比共享文件夹更稳**。原因不是 FTP 本身好，而是它能被设计成"只取一个固定文件"，绕开 FTP 的两个经典坑。

### 2.2 三个坑与规避

| 坑 | 规避方式 |
| --- | --- |
| **中文文件名乱码**（学校 FTP 多为 GBK/Serv-U） | **不用中文名**。固定用 `manifest.json` + `data.cbpack`，纯 ASCII |
| **列目录（LIST）解析麻烦**（不同服务器格式不同） | **不列目录**。直接按固定路径 `RETR manifest.json`，取不到就认为"没有更新" |
| **被动模式/防火墙** | `UsePassive = true`、`Timeout = 8000ms`、失败静默回退到本地缓存，**绝不阻塞启动** |

### 2.3 实现选型

用 .NET 内置 `System.Net.FtpWebRequest`（net8 仍可用），**不引入 FluentFTP**。理由：离线版不想增加 NuGet 依赖与自包含体积；而且我们只用 `RETR` 两个固定文件，不需要 `LIST` / `MLSD` / 断点续传。

> 若将来发现学校 FTP 需要 TLS（FTPS）或 `RETR` 被限制，再换 FluentFTP，接口已由 `IFeedSource` 隔离，不影响上层。

### 2.4 三种传输统一成一个接口

```
IFeedSource
  ├─ FolderFeedSource   局域网共享文件夹（\\server\课表）或本地/U盘路径
  ├─ FtpFeedSource      ftp://user:pwd@host:port/path/
  └─ (预留) HttpFeedSource  将来二一或网盘
```

统一契约（**只有两个动作**）：

```
Probe()  → 读 <源>/manifest.json，返回 (版本号 / 时间 / data 的 SHA-256)
Fetch()  → 若 Probe 的 SHA-256 与本地记录不同，RETR <源>/data.cbpack
```

这样 U 盘、共享文件夹、FTP 三者走完全相同的代码路径，**判断"有没有更新"完全不依赖文件时间戳**（FTP 的时间戳常因时区/服务器设置错乱）。

### 2.5 服务器端约定（你要在 FTP 上建的结构）

```
/课表/                       ← 建议路径全用英文：/schedule/
    manifest.json            ← 几十字节，每次发布时重写
    data.cbpack              ← 数据包（zip），几 MB
    archive/2026-10-31.cbpack ← 历史留档（可选，只增不删）
```

`manifest.json` 示例：

```json
{
  "schema": 1,
  "school": "东凤中学",
  "builtAt": "2026-10-31T18:00:00+08:00",
  "dataSha256": "9f2c…",
  "dataSize": 384122,
  "note": "第9周（10/26–11/01）临时课表"
}
```

### 2.6 ★ FTP 上到底放什么：Excel 直投 vs 数据包

这是最容易选错的一步。先看实测数据（Release 构建，本机 125% 缩放）：

| 操作 | 耗时 | 体积 |
| --- | --- | --- |
| 解析并合并三份总课表（90 班） | **1090 ms** | 三份 xlsx 共 **50 KB** |
| 单份总课表解析 | 197 ms | 17 KB |
| 解析 1 份临时课表（39 条覆盖） | 225 ms | 17 KB |
| 由 90 班底表重建教师表（282 位） | **12 ms** | — |
| 底表序列化 / 反序列化 | 38 / 22 ms | **452 KB** |
| 教师表序列化 | — | 493 KB |

三条反直觉结论：

1. **教师表根本不需要分发**：重建只要 12 ms。数据包不带 `teacher_schedule.json`，体积立刻少一半。
2. **机房解析完全扛得住**：30 台各自解析 1.1 秒，CPU 无压力（ClosedXML 已随自包含发布打包，教室机不需要装 Office）。
3. **体积差不是问题**：数据包 452 KB × 30 台 = 13.5 MB，局域网/FTP 几秒的事。真正该纠结的不是大小，是**一致性**。

#### 三种布局对比

| | A 纯 Excel 直投 | B 纯数据包 | **C 混合（推荐）** |
| --- | --- | --- | --- |
| FTP 上放 | 3 份总课表 + 临时课表 xlsx | `data.cbpack` + `manifest.json` | `source/` 放 xlsx，`publish/` 放数据包 |
| 教务习惯 | 零改变，直接拖 | 必须有人转换 | 零改变，直接拖 |
| 解析发生在 | **30 台各自解析** | 主控机 1 次 | 主控机 1 次 |
| exe 版本不一致时 | ★ **同一份 xlsx 解析出不同课表** | 结果恒定 | 结果恒定 |
| 发布前能否预览 | 不能 | **能**（"90 班 / 39 条 / 10-26~11-01"） | 能 |
| 出错能否一键回退 | 不能 | 能 | 能 |
| 半传/被占用文件 | ★ 会拿到半截 xlsx | 可用 `.tmp` 再改名规避 | 同 B |
| 生效区间从哪来 | ★ **无处存放**（见下） | 打包时写进 manifest | 打包时写进 manifest |
| 教务能自己发布吗 | 能 | 不能 | 能（但需主控机转一次） |

#### ★ 纯 Excel 方案的四个死结

**死结 1：临时课表的"生效区间"没地方放。**
`（八年级）-全校班级临时总课表.xlsx` 文件名里没有日期，教务每周覆盖同一个文件。
教室机自动导入时只能猜："取当前周"。那么——

- 周五上传下周的临时课表 → 被当成"本周"，**下周反而没有调代课**；
- 周一补传上周的 → 被当成"本周"，**本周的课全错**。

要用 Excel 直投，必须靠**目录名承载周次**（`/schedule/2026-10-26/`），这是硬约定，不能靠猜。

**死结 2：exe 版本漂移。**
本次刚发现的七年级 13 列 bug 就是活例：旧版 exe 解析七年级会丢每天第 8 节。
如果 30 台里有 3 台没升级，同样的 xlsx 会解析出**三份不同的课表**，而且没人看得出来。
数据包方案下解析只在一台机上做，天然规避。

**死结 3：半传文件与 `~$` 锁文件。**
教务用 Excel 编辑时，文件被锁且同目录会出现 `~$xxx.xlsx`；服务器正在写入时更是半个文件。
教室机自动去读，轻则跳过、重则把空表当新课表。数据包可以用"先传 `.tmp` 再改名"，Excel 直接保存做不到。

**死结 4：错了没人知道。**
30 台无人值守，某台解析失败 → 静默保留旧课表 → 学生看到的是错的。没有任何回执。

如果一定要纯 Excel 直投，至少补这四条保险：
1. 目录名带周起始日（`2026-10-26/`），程序按目录推区间；
2. 忽略 `~$` 开头与被占用的文件，解析失败就跳过并保留旧数据；
3. 导入后校验 `班级数 == 90`，不符则放弃本次；
4. 状态栏常驻一行"数据源：FTP /source/ 90 班，最后更新 10-31 18:02"，出问题能一眼看到。

#### C 方案：全自动链路（推荐）

FTP 上建两个目录，人和机器各读一个：

```
/schedule/
    source/                         ← 教务/曾老师往里丢 Excel（人看、留档）
        七年级-总课表.xlsx
        八年级-总课表.xlsx
        九年级-总课表.xlsx
        2026-10-26_临时课表_八年级.xlsx     ← 文件名带周次，供自动发布识别
    publish/                        ← 程序产物，30 台只读这里
        manifest.json
        data.cbpack
    archive/
        2026-10-31.cbpack           ← 每次发布留一份
```

链路（主控机 = 任意一台已登录的机器）：

```
教务丢 Excel 到 source/
      ↓（主控机启动时 + 每 30 分钟扫描 source/ 的 SHA-256）
解析 → 校验 90 班 → 自动发布 publish/data.cbpack + manifest.json
      ↓（其余 29 台启动时 + 每 30 分钟 Probe publish/manifest.json）
发现 dataSha256 变了 → 下载 → 校验 → 预览（可配静默）→ 应用
```

好处：

- 教务**零改变**（继续丢 Excel）；
- 30 台只消费**已验证的数据包**，不受 Excel 格式波动与 exe 版本影响；
- 出问题能回退（`archive/` 里留了每一版）；
- 主控机没开机时，其余 29 台继续用本地数据，**不会更糟**。

代价：需要一个"主控机"角色，且它得开机。若某周主控机整天没开，其余机器就停在上一版——
这可以用"任一台机器都可以当发布机"来缓解（谁先发现 `source/` 有变化谁发布，用 FTP 上的
`publisher.lock` 带时间戳简单互斥）。

### 2.7 客户端行为

| 时机 | 动作 |
| --- | --- |
| 启动后 30 秒（错开 30 台同时拉） | Probe → 有变化则 Fetch → 预览确认（可配为静默）→ 应用 |
| 每 N 分钟（默认 30） | 同上，只在有变化时才动作 |
| 手动"立即检查更新" | 立即执行，把结果显示在状态栏（失败要说清是哪一步：连不上 / 没有 manifest / 校验和不符） |
| 离线 / 服务器不可达 | **什么也不做**，用本地数据继续跑（这是离线版的底线要求） |

## 3. ★ 数据包为什么要分两类（你最需要先理解的部分）

### 3.1 一个具体场景

你在 **302 班**的电脑上配好了这些：

- 显示 **八年级(14)班** 的课表
- 悬浮窗拖到**右侧、420×760、半透明**
- 主题 **深海蓝**
- 作业公示填了 **"数学：练习册 P32–P35"**
- 快捷启动加了 **"希沃白板"**
- 登录密码改成 **138000**

现在要把课表铺到 **303 班**。如果"整个 AppData 打包拷过去"，303 班开机后会变成：

> 显示八年级(14)班 · 窗口跳到右侧同一位置 · 作业写着 302 班的数学作业 · 快捷方式指向 302 班的路径 · 密码也变成 302 的

**这些不是"课表"，是"这台机器的身份和使用习惯"。** 必须分开。

### 3.2 分类原则

判据只有一句：**"这一项，203 班和 302 班应该一样吗？"**

- **一样** → 公共数据，跟着数据包走，每次更新覆盖
- **不一样** → 本机设置，永远不放进数据包

### 3.3 具体分类表

| 内容 | 类别 | 说明 |
| --- | --- | --- |
| `schedule.json` 底表（90 班） | **公共 · 覆盖** | 全校一份 |
| `teacher_schedule.json` 教师表 | **公共 · 覆盖** | 从底表派生，导入后自动重建，不必单独分发 |
| `overrides.json` 里 `Source=temp/remote` | **公共 · 按区间合并** | 本周/下周的调代课 |
| `overrides.json` 里 `Source=manual` | **本机 · 保留** | 本班老师自己临时改的，不能被别班覆盖 |
| `overrides.json` 里 `Source=basePatch` | **公共 · 覆盖** | 长期改课，全校一致 |
| `notifications.json` 通知公告 | **公共 · 可选勾选** | 全校通知要同步；本班通知不该外传 → 见 §3.4 |
| `settings.json: SemesterStartMonday` | **公共 · 覆盖** | 开学周，全校必须一致（否则单双周全错） |
| `settings.json: Theme` | **公共 · 可选** | 想统一界面风格就同步 |
| `settings.json: SelectedClass / SelectedTeacher / ScheduleKind` | **本机 · 保留** | ★ 这台机器显示哪个班，最不能覆盖 |
| `settings.json: ScheduleLayout / NotificationLayout` | **本机 · 保留** | 各教室分辨率、屏幕朝向不同 |
| `settings.json: Username / Password / 密保` | **本机 · 保留** | 见 §3.5 |
| `settings.json: AutoStart / LaunchFullscreen / LaunchLocked / AutoShow*` | **本机 · 保留** | 开机行为 |
| `settings.json: HwWin* / MsWin*`（便签位置尺寸锁定） | **本机 · 保留** | |
| `settings.json: QuickLaunchers` | **本机 · 保留** | 路径各机不同 |
| `settings.json: DisplayDateMode / FixedDisplayDate` | **本机 · 保留** | 调休时单台设置 |
| `settings.json: Reminder` 提醒 | **公共 · 可选** | 作息时间全校统一，但开关各机自定 |
| `settings.json: Backdrop` 桌面背景 | **本机 · 保留** | |
| `homework.json` 作业 | **绝不打包** | 本班独有内容 |
| `missing.json` 缺交 | **绝不打包** | |
| `settings.json: CustomNotes` 自定义便签 | **本机 · 保留** | 教师寄语等，各班主任自己写 |
| `desktop_backdrop.png` | **不打包** | 应用后自动重绘（2.4 MB，没必要传） |

### 3.4 通知公告要不要同步？

三种可选，建议默认选 **B**：

| 方案 | 行为 | 适用 |
| --- | --- | --- |
| A 不同步 | 通知纯本机 | 通知都是班主任自己发的 |
| **B 分来源（推荐）** | 通知里已经可能有级别/来源字段；标为"全校"的同步，"本班"的保留 | 既能看到校务通知，也能自己发 |
| C 全部同步 | 全校通知一致 | 但会把 302 班自己发的通知推到 303 班 |

> 实施前需要确认 `Notification` 模型有没有"来源/范围"字段；没有就加一个 `Scope: school/local`，工作量很小。

### 3.5 密码怎么办

`Username/Password` 是本地明文的单账号（默认 `admin/000`），**不是安全机制，只是防止学生乱点**。

- 数据包**不带**密码 → 30 台机器各自保留自己的密码（多数会是默认 `000`，也就无所谓）
- 但如果 30 台要用同一套密码，那就需要单独一个"**整机克隆包**"（见 §5.3），由安装人员刻意使用

### 3.6 两个包，别混成一个

| 包 | 文件名 | 内容 | 用在哪 |
| --- | --- | --- | --- |
| **数据包** | `data.cbpack` | 只有"公共"那几项 | **每周例行分发**，30 台全都装 |
| **整机克隆包** | `profile.cbprofile` | 上面所有内容 + 本机设置（含密码、布局、班级） | **只在装新机/换机时用一次**，装完必须立刻改班级 |

> 现场最容易出的事故：把 `profile.cbprofile` 当周更包发下去 → 30 台全部显示成同一班。
> 所以两者**导入入口要分开**（数据包在"数据管理"页，克隆包在"用户中心 → 高级"里，且带红色警告）。

## 4. 方案一：如何合并三个年级的课表

### 4.1 目标

一次操作（或一次选三个文件），得到 **90 个班**的底表；重复导入不产生重复班、不丢班。

### 4.2 三步改造

**第 0 步（前置，必修）：修 12 列硬编码**（见 §1.2）。

**第 1 步：`BtnImport` 改"按班合并"**——与 r8 单班导入完全同款：

```
现有底表 cur = LoadSchedule() ?? new
foreach (导入文件 f in 选中的文件们)
    sf = Import(f)
    foreach (班 c in sf.Classes)
        cur.Classes.RemoveAll(x => x.ClassName == c.ClassName)
        cur.Classes.Add(c)
cur.ImportedAt = now
SaveSchedule(cur)
```

**第 2 步：文件选择改为多选 + 记忆上次目录**

- `OpenFileDialog { Multiselect = true, Filter = "Excel (*.xlsx)|*.xlsx" }`
- 一次勾选七/八/九三份，逐个解析后合并
- 也保留"只导一份"的用法（合并逻辑天然支持）

### 4.3 合并时必须处理的 5 件事

| # | 事项 | 规则 |
| --- | --- | --- |
| 1 | **同名班冲突** | 后导入的替换先导入的，并在状态栏列出来：`覆盖同名班：八年级(14)班` |
| 2 | **班级数校验** | 状态栏必须回显 `原有 30 个班 → 现共 90 个班`（这是唯一能让操作者一眼看出"有没有丢"的信息） |
| 3 | **教师表重建** | 合并完成后，用**合并后的完整底表**重建 `teacher_schedule.json`（`TeacherExtractor.Build(cur)`）。现在的代码是拿单份 `sf` 建，合并后必须换成 `cur`，否则教师表只有最后一个年级的老师 |
| 4 | **来源记录** | `ScheduleFile.SourceFile` 只有一个字符串，建议加 `List<string> SourceFiles`，记录"合并自 3 份"；JSON 向后兼容（旧字段保留） |
| 5 | **长期改课冲突** | 若已存在 `basePatch`（§6），重新导入底表时弹窗：`检测到 N 条长期修改，新底表可能已包含这些改动 → [保留] [清除]` |

### 4.4 年级顺序与班级排序

`ClassNames` 下拉的顺序 = `cur.Classes` 的顺序。按导入顺序会出现"八年级、九年级、七年级"这种乱序。

建议合并后按 **年级（七→八→九）+ 班号数字** 排序一次：

```
七年级(1)…(30)，八年级(1)…(30)，九年级(1)…(30)
```

注意班号是 `(10)` 这类带括号数字，要按**数值**排而不是字符串排（否则 `(10)` 排在 `(2)` 前面）。

### 4.5 验证清单（实施后必须过）

- [ ] 七年级任意班周一有第 8 节（对比 Excel 第 14 列）
- [ ] 三个年级各 30 班，共 90 班，无重名
- [ ] 重复导入同一份 → 班级数不变（幂等）
- [ ] 教师表人数 = 三个年级去重后的教师数，抽查某位跨年级任课老师能看到三个年级的课
- [ ] 单班导入 / 单教师导入仍正常（不能把这两个入口改坏）
- [ ] 临时课表导入后，落到对应年级的班上（九年级临时表不会打到八年级）

### 4.6 风险与回退

- 合并是**破坏性写盘**，导入前自动备份 `schedule.json` 到 `backup/schedule-<时间戳>.json`（与 §5 的备份机制共用）
- 若状态栏班级数少于预期，提供"撤销本次导入"（恢复刚才的备份），比让人重导三份可靠

## 5. 方案二：如何完善导出与备份

### 5.1 三个不同用途，别混成一个按钮

| 用途 | 名字 | 频率 | 内容 |
| --- | --- | --- | --- |
| ① 每周铺数据 | **导出数据包** / 导入数据包 | 每周 1 次 | 只有公共数据（§3.3） |
| ② 装新机/换机 | **整机克隆** | 极少 | 公共 + 本机设置 |
| ③ 出事回滚 | **自动备份 / 恢复** | 每次写盘前 | 单个/全部 JSON |

### 5.2 数据包格式（`data.cbpack`）

外层是 zip，内部结构：

```
manifest.json        包内清单 + 校验和
schedule.json
teacher_schedule.json
overrides.public.json     ← 只含 temp / remote / basePatch，不含 manual
notices.school.json       ← 只含 Scope=school 的通知（若选 B 方案）
meta.json                包内公共设置片段（开学周 / 主题 / 提醒）
```

`manifest.json` 示例：

```json
{
  "schema": 1,
  "kind": "data",
  "builtAt": "2026-10-31T18:00:00+08:00",
  "builtBy": "主控机-教务处",
  "classCount": 90,
  "overrideCount": 39,
  "overrideRange": "2026-10-26~2026-11-01",
  "files": [
    { "name": "schedule.json", "sha256": "…", "size": 334547 },
    { "name": "overrides.public.json", "sha256": "…", "size": 5521 }
  ]
}
```

### 5.3 导入时的行为（重点在"不破坏本机"）

```
1. 读 manifest → 校验每个文件的 SHA-256（不符 = 包损坏/被改，直接拒）
2. 展示预览：90 个班 / 39 条调代（10-26~11-01）/ 通知 3 条 / 开学周 2026-08-31
   → 用户确认
3. 自动备份当前数据到 backup/<时间戳>/
4. 写入：
   - schedule.json       覆盖
   - teacher_schedule.json 覆盖（或直接按新底表重建）
   - overrides           ★ 合并而不是覆盖：
                          删掉本机 Source∈{temp,remote,basePatch} 中「与包内区间重叠」的
                          加入包内记录
                          本机 Source=manual 一律保留
   - notices             按 Scope 合并（school 覆盖，local 保留）
   - meta                只写白名单字段（SemesterStartMonday / Theme / Reminder）
   - settings.json 其它字段（SelectedClass / 布局 / 密码 / 作业…）→ 不动
5. 重算教师表、刷新界面、状态栏回执
6. 记下 dataSha256，下次 Probe 时用它判断"是否已是最新"
```

**为什么 overrides 要"区间重叠"而不是"整类删"**：r8 已把导入改成 `RemoveAll(Source=="temp" && OverlapsRange(本次区间))`。数据包沿用同一规则，这样"上周的调代课"和"下周提前发的调代课"能共存。

### 5.4 自动备份（独立于数据包）

| 时机 | 动作 | 保留 |
| --- | --- | --- |
| 任何一次"覆盖型写盘"前 | 把将被覆盖的 JSON 复制到 `backup/<yyyyMMdd-HHmmss>/` | 最近 20 份，超出的删最旧 |
| 每次成功导入数据包后 | 同上 + 记 `manifest.json` 副本 | 同上 |

恢复入口：`数据管理 → 备份与恢复`，列表显示时间/班级数/调代条数，选中即可回滚单份或全部。

> 这同时补上了 06 设计 §4.11 里"版本回退自动备份"的缺口，也补上 §4.8 说的"迁移前备份 `overrides.json.bak`"。

### 5.5 主控机"一键发布"流程（最终形态）

```
[导入 3 份总课表] → 90 班
[导入本周临时课表] → 选生效区间
[导出数据包] → 选目标：本地文件 / 共享文件夹 / FTP / U 盘
    → 自动写 manifest.json（含 SHA-256）
    → 若目标是 FTP/共享文件夹，同时更新 archive/
```

导出时若目标是 FTP/共享文件夹，**先写 `data.cbpack` 再写 `manifest.json`**（避免各机读到"新 manifest + 旧 data"）。

## 6. 方案三：长期改课（"原始课表 / 临时课表"双入口）

### 6.1 你的想法能不能实现：能，而且是正确的建模

你描述的语义是：

> 原始课表（底表）默认永久有效；在原始课表里改一格 → 原底表从某日终止、新底表从该日生效，等于**追加一张底表**。

这在数据建模里叫"**生效日版本化**"（effective-dated versioning）。它有个很好的性质：**任何时刻的课表都可以由"某日之前最后一张版本"唯一确定**，不需要冲突检测、不需要"谁覆盖谁"。

### 6.2 但不要真的存"多份底表"

如果真把 `schedule.json` 改成 `class → 版本列表`：

| 代价 | 具体 |
| --- | --- |
| 结构变更 | `ClassSchedule.Data` 要变成 `Data[fromDate][day][period]` |
| 全部读取点要改 | `BoardBuilder`、`WeekBuilder`、`TeacherExtractor`、`BackdropRenderer`、`IsClassTimeNow`、打印… |
| 文件膨胀 | 90 班 × 每班每次改动存全量 → 一份改动可能让 schedule.json 从 334 KB 涨到几 MB |
| 与现有机制重复 | 你已经有 `overrides.json` + `OverrideExpander` 在做"按日期求交"，再开一套并行机制必然分叉 |

### 6.3 推荐：用"开放区间"表达长期改课

在**现有** `LessonOverride` 上加一个来源值，语义扩一条规则即可：

```csharp
Source = "basePatch"        // 长期改课（"改底表"）
ValidFrom = 生效日           // 从哪天起
ValidTo   = null            // ★ null = 开放结束 = 一直有效，直到出现更新的 basePatch
```

**"取最新版"规则**（新增，现有 `MapForDate` 只做"求交"）：

```
同一格子可能有多条 basePatch：
  B1  ValidFrom=10-15, ValidTo=null, 科目=地理
  B2  ValidFrom=11-01, ValidTo=null, 科目=生物      ← 11/01 又改了一次

查 10-20 → B1（B2 还没开始）
查 11-05 → B2（两者都满足 from<=date，取 ValidFrom 最大的一条 = 最新版）
```

算法（在 `OverrideExpander` 里加一个分支）：

```
候选 = all.Where(x => x.Source=="basePatch"
                   && x.ValidFrom <= date
                   && (x.ValidTo == null || x.ValidTo >= date))
同 CellKey 取 ValidFrom 最大的一条
```

这样"原底表在某日终止"是**自动成立**的：B2 生效那天起，"取最新"自然不再选 B1，你不需要去改 B1 的 `ValidTo`。

### 6.4 三层叠加后的显示优先级

```
① 本周临时（Source=temp/remote/manual，有明确 ValidFrom~ValidTo）  ← 最高，这是"这周实际"
② 长期改课（Source=basePatch，ValidTo=null，取最新版）              ← 次高
③ 底表（schedule.json）
```

同一格三层都有值时，显示 ①；只有 ②③ 时显示 ②；只有 ③ 显示底表。

### 6.5 界面：周视图加"原始 / 临时"切换

| 模式 | 渲染 | 拖动 / 右键修改后写入 |
| --- | --- | --- |
| **临时课表**（默认） | ① + ② + ③ | `Source=manual`，区间=**当前显示周**（或弹窗选） |
| **原始课表** | ② + ③（**不含本周临时**） | `Source=basePatch`，`ValidFrom`=用户选的"从哪天起"，`ValidTo=null` |

原始模式必须做**三重防误操作**，否则一定出事（老师以为在改本周，其实改了永久）：

1. 周视图标题变红：`原始课表（长期生效，改动会影响所有周）`
2. 保存前弹确认：`将把「八年级(14)班 周三 第3节」从 11月3日 起长期改为「生物 / 张三」。此修改对所有后续周生效，不只是本周。确定？`
3. 状态栏与格子上角标 `长期`（橙色小标签），与本周临时的 `调/代` 区分

### 6.6 需要配套处理的 4 处

| 处 | 处理 |
| --- | --- |
| 教师表 | `TeacherExtractor` 仍按纯底表生成；但教师**查看**时要叠加 basePatch（`TeacherOverrideApplier` 已在这条链路上，增加 basePatch 源即可） |
| 桌面背面 | 走同一个 `MapForDate` → 自动生效，无需改 |
| 复习"底表被重新导入" | 见 §4.3 第 5 条，弹窗询问保留/清除 basePatch |
| 撤销 | 长期改课最容易"改错了找不回来"。提供 `原始课表 → 右键 → 查看本格修改历史`，可删掉某条 basePatch 即恢复到上一版 |

### 6.7 成本估计

| 项 | 改动量 |
| --- | --- |
| `OverrideExpander` 加"开放区间 + 取最新"分支 | ~40 行 |
| 周视图加模式切换 + 写入目标分流 | ~60 行 |
| 原始模式标题红字 + 确认对话框 + 格子角标 | ~40 行 |
| 本格修改历史（可延后） | ~80 行 |

**结论：可行，且比"真版本化底表"便宜约 80%。** 唯一的语义让步是：底表本身仍只有一份（只是上面叠了长期补丁），不能"翻到 10 月份去看当时的底表"。若将来真需要审计历史版本，再在此基础上加归档。

## 7. 你提的其余三项，怎么落

### 7.1 周起始日可选、默认周日

- `WeekHelper` 已经支持 `WeekStart(date, weekStartDay)`，只是所有调用都传默认周一
- **必须成对改**：`WeekBuilder` 的列映射（现在 `dayIdx = 0..6` 按周一写死）、`WeekView.StartOfWeek`、以及"本周"区间计算
- 新增设置项 `AppSettings.WeekStartDay`（0=周日 … 6=周六，默认 0）
- 风险点：`DayIdx` 是**日历星期**（周一=0…周日=6），**绝不能**因为"周起始日变了"而改 `DayIdx` 的算法（06 设计里的铁律）。变的只有"一次显示 7 天的窗口从哪天开始"
- 副作用（要接受）：默认周日打头后，周日列排在最前，周一不再在第一列；标题写"10/25–10/31"

### 7.2 清除按钮改成"弹对话框选三种范围"

```
清除调代课
  ○ 清除当前显示的这一周（10/26–11/01）      ← 默认
  ○ 清除指定日期范围  [2026-10-26] ~ [2026-11-08]
  ○ 清除全部（含长期改课）                    ← 红色，二次确认
  [ ] 连同远程同步来的调代课一起清除（否则写屏蔽清单，见 06 §4.10 铁律 4）
```

- 三种模式都用 `OverrideExpander.ForCellInWeek` / 新增 `InRange(from,to)` 定位，**不拼字符串比 Key**
- "清除全部"必须把 `basePatch` 单列一行说明，因为那是长期改动，删了影响整个学期
- 除"本周/指定范围的 temp"外，其余删除都自动备份 `overrides.json`

### 7.3 升级一次性提醒

场景：从旧版升级到 r8 后，旧 `overrides.json` 里的记录没有 `ValidFrom/ValidTo`，`Store.MigrateOverrideRanges` 会按 `UpdatedAt` 归周 → 很可能一条都不在当前周 → 用户看到"调代课全没了"。

做法（`AppSettings.OverridesMigratedAt` 为空时触发一次）：

```
检测到 N 条历史调代课（升级前录入，没有生效日期）。
它们已被归入各自的录入周，可能不属于本周。
  [全部归入本周]（推荐，若你确认本周仍有效）
  [保持原样]（按录入周，过期即不显示）
  ☐ 不再提醒
```

- 记录写入 `OverridesMigratedAt` 后永不再弹
- **附赠**：`数据管理` 页顶部常驻一行 `数据源：Excel 底表 90 班 · 调代 39 条（本周生效 12 条）`，比任何弹窗都更能消除"数据丢了"的错觉

### 10.5 O4 周起始日可选（默认周日）2026-10-31 完成

**核心难点：列号 ≠ `DayIdx`**

数据层的 `DayIdx` 永远 0=周一 … 6=周日（课表 Excel 就是这么导入的，改它等于把整个课表数据重排）。
而"这一周从哪天开始"是**显示层**的事。所以：

```
第 col 列的日期 = weekStart.AddDays(col)
第 col 列的 DayIdx = ((int)日期.DayOfWeek + 6) % 7
```

以前 `WeekBuilder` 直接拿 `dayIdx` 当列号（`thatDate = monday.AddDays(dayIdx)`），
一旦把周起始日改成周日，就会**整列错位一天**。现在 `WeekGridData` 多了一个
`ColumnDayIdx`（7 个列各自对应哪个 `DayIdx`），`WeekView.BuildGrid` 按它取格子。

**改动清单**

| 位置 | 改动 |
| --- | --- |
| `AppSettings.WeekStartDay` | 新增，0=周日 … 6=周六，默认 **0（周日）** |
| `WeekHelper.DefaultWeekStartDay` | 周一 → **周日**；新增 `NormalizeStartDay` / `StartDayName` / `WeekWindowOf(weekStart)` |
| `WeekBuilder.BuildWeek` | 参数 `monday` → `weekStart`；按日期推 `dayIdx`，填 `ColumnDayIdx` |
| `WeekView` | `StartOfWeek()` 删除，改用 `WeekHelper.WeekStart(now, 设置)`；`Rebuild` 里按新设置重新对齐当前周（幂等，不动就原地） |
| `OverrideExpander.ForCellInWeek/ForClassInWeek` | 改用 `WeekWindowOf(weekStart)`——从调用方给的那一天自己推 7 天，不需要把设置传一路 |
| `LessonOverrideWindow` / `WeekView` 的清除与写入 | 同上，一律 `WeekWindowOf(_weekStart)` |
| `ScheduleWindow.UpsertOverride` | 按设置里的周起始日算"本周"（与周视图同一段日期） |
| `EffectiveRangeWindow`（导入临时课表选区间） | "本周"跟设置走，否则页面周日开头、对话框周一开头，会选错周 |
| `SchedulePackage.Export` | 无调代课时写的默认区间跟设置走 |
| `MainWindow.xaml` 显示设置 | 新增「课表周视图 → 一周从 [周日/周一/…/周六] 开始」 |

**"第 N 周"标签的算法**

不能再用 `TeachingWeek(weekStart)`：周日开头时，`weekStart`（周日）属于**上一个**教学周。
改为取这一周的中间那天：`TeachingWeek(weekStart.AddDays(3))` —— 周日开头时取周三，
周一开头时取周四，都落在"这一周多数天数所在的教学周"里。

**实测**

| 项 | 结果 |
| --- | --- |
| 周日开头，weekStart=2026-11-01 | 列 DayIdx = `6,0,1,2,3,4,5`；表头 = 周日 11/01 … 周六 11/07 ✔ |
| 同上，周二第1节 | 落在 `DayIdx=1` 的格子里，科目 = 道德与法治 ✔ |
| 只在 11-03（周二）生效的调课 | 在周日开头的这周**显示**在周二格；在 10/26–11/01 那周**不显示** ✔ |
| 周一开头，weekStart=2026-10-26 | 列 DayIdx = `0..6`；表头 = 周一 10/26 … 周日 11/01 ✔ |
| 7 种起始日的窗口 | 每种都是 7 天且都包含被查询日期 ✔ |
| 界面实测（默认周日） | 周视图表头 周日 10/25 … 周六 10/31，"第9周" ✔ |
| 界面实测（改成周一） | 表头 周一 10/19 … 周日 10/25，"第8周" ✔（设置改完立即生效，无需重启） |

### 10.6 修「发布机不落地自己」+「缺底表静默凑数」2026-10-31 完成

**用户报的现象**：已设好共享文件夹并生成数据，更新后本机看不到调代记录。

**查到的三件事**

| # | 事实 | 性质 |
| --- | --- | --- |
| 1 | 八年级临时课表 30 个班只有 12 个班带 `(调)/(代)`，共 39 处；用户班 八(23)班 **0 处** | 源数据如此，不是 bug |
| 2 | 本机 `overrides.json` = 0 条，而远端包里有 391 条 | **真 bug（发布机不落地）** |
| 3 | 包内底表只有 30 个班（八年级），但覆盖涉及 71 个班 → 352 条属于底表里没有的班 | **真 bug（缺底表静默凑数）** |

**Bug 1：发布机只上传、不落地，还顺手把摘要记成"已应用"**

`SourcePublisher.Publish` 的注释写着"本类不改本机数据"，而 `BtnPublishNow_Click` 在发布成功后执行：

```csharp
stp.LastAppliedSha = r.DataSha;   // 记成"我已是这个版本"
```

于是发布机每 30 分钟检查一次，永远得到"已是最新"——**它自己反而永远拿不到新调代课**。
隔离环境实测：机 A 36 条 → 发布 → 仍是 36 条 → 再检查 `HasUpdate=False`。

修法：给 `Publish` 加 `applyToLocal`（默认 true），上传或"远端已最新"后，把刚打的包
`Inspect` + `Apply` 到本机；`Result` 回传 `LocalApplied / LocalSkipped / LocalError / LocalBackupDir`。

- **本机同步失败时不写 `LastAppliedSha`**——让下次自动检查重新拉一遍这个包自愈，
  否则会永远卡在"已是最新"、且本机是坏的。
- 摘要由 `RecordReleased()` 在发布器内部写，不再依赖界面，任何调用方行为一致。
- 本机已经是这个版本（且 public 调代条数一致）时跳过落地，省一份备份。

**Bug 2：`source/` 没有总课表时，静默退回本机底表**

底表班数 30、覆盖 71 个班，包照样发出去，教室机应用后 391 条里只有 39 条能显示。
修法分两层：

1. **发布前** `SourcePublisher.Scan(sourceDir)` 预检，在确认框里列清
   总课表几份 / 临时课表几份 / 生效周范围 / 哪些临时表文件名没有日期前缀；
   缺总课表时明确写"底表只能用本机这份（N 个班），其他年级发不出去"，并把确认框图标换成警告。
2. **发布后** `Result.OrphanClasses / OrphanOverrides` 统计"覆盖里有、底表里没有"的班，
   在消息里给出具体班级名，并由界面弹窗列出所有 `Warnings`（不再只塞进状态栏）。

**实测（隔离环境，两套独立目录）**

| 场景 | 预检 | 发布结果 | 本机落地 | 再检查 |
| --- | --- | --- | --- | --- |
| A：`source` 只有 3 份临时表 | `BaseFromLocal=True`，⚠ 底表退回本机 30 班 | 30 班 / 391 条，⚠ 孤儿 59 班 352 条 | 30 班 / 391 条（仅 40 条有效）| `HasUpdate=False` |
| B：`source` 补齐三份总课表 | `BaseFromLocal=False`，无风险 | **90 班** / 391 条，孤儿 0 | **90 班** / 392 条（含 1 条 manual）| `HasUpdate=False` |
| B 场景覆盖有效性 | — | — | **392 / 392 条都能落到班级上** | — |
| B 场景手工调课 | — | — | 保留 1 条 | — |

对照修改前：同样是发布动作，本机 overrides 保持在 36 条不动，而远端已经是 391 条。

**顺带说明**：本机 `overrides.json` 在 22:55 被写成 `[]`，但底表时间还是 16:59、
也没有生成"导入数据包"备份——说明那次不是 `Apply`，而是「清除全部临时调课 / 代课」按钮。
`Apply` 一定会同时重写底表并留备份，所以用这两个特征可以区分。

### 10.7 source 目录变化自动发布 + 临时表日期对齐 2026-10-31 完成

**用户报的现象**：把检查间隔设成 3 分钟，"好像没生效"；最后手点「发布到数据源」才成功。

**查下来是三件事叠在一起**

| # | 问题 | 性质 |
| --- | --- | --- |
| 1 | 保存允许 0~1440 分钟，运行时 `Math.Clamp(m, 5, 720)` → **设 3 实际按 5 跑** | 真 bug（本轮未改，见下）|
| 2 | 输入框 ToolTip 写"0 = 只在启动时检查一次"，代码同样夹到 5 → **设 0 反而每 5 分钟** | 真 bug（本轮未改）|
| 3 | 自动更新**只拉不推**：它读的是 `manifest.json`，source 里的 Excel 只有发布机才读 | 设计缺口（本轮已补）|

第 3 条才是主因：用户在 source 里放了总课表和新的临时表，但没人打包上传，
远端还是旧包，于是自动检查每次都只能回"已是最新"——等 3 分钟、30 分钟都一样。
再加上发布机的 `LastAppliedSha` 就是自己发布的摘要，它天然永远"已是最新"。

**做了什么**

1. **`SourcePublisher.SourceFingerprint(dir)`**
   文件名 + 大小 + 最后写入时间 → SHA-256 前 16 位。不解析内容，几十毫秒算完；
   不存在的目录返回空串。

2. **`MainWindow.TickSourcePublish()`**（每 30 秒一跳，**不受 `_updNextAt` 限制**）
   - 指纹与"已处理过"的相同 → 什么都不做
   - 第一次见到新指纹 → 记下 pending，等下一跳
   - **连续两次扫描一致** → 才发布（Excel 保存过程中大小/时间会变，立刻读会读到半截文件）
   - 因此放完 Excel 最多 **60 秒**就会自动发布，不用等"检查远端"那个间隔

3. **`AutoPublishAsync()`** 发布成功后：刷新界面（`ApplyImportedSchedule` + `RaiseScheduleChanged`）、
   回显"已自动发布：N 个班、调代 M 条"。**失败不记指纹**（下一跳重试），且把错误显示在状态行，
   不静默吞掉。

4. **`AppSettings.AutoPublishOnSourceChange`**（默认 true）+ 设置窗口新增「自动发布」复选框，
   只在勾了「发布机」时出现。

5. **临时课表文件名日期对齐到「所在周起始日」**
   教务改本周临时表习惯写当天（如周三 `2026-10-29`）。按原来的"该日期起 7 天"，
   区间会变成 `10-29~11-04`：**既漏掉本周前三天，又吃掉下周前三天**。
   现在统一 `WeekHelper.WeekStart(文件名日期, WeekStartDay)` → 全部落到 `10-25~10-31`（周日开头）。

6. **发布时间按 Key 去重**
   同一格同一周被两份临时表都提到时（本周表后来改过一次），包内不再出现两条同 Key 记录。
   否则 `manifest.OverrideCount` 报 644，教室机落地后只有 605 条，对不上；
   发布机自己也会因为"条数不一致"而每次多重落地一遍、白占一份备份。

7. **`Precheck.Describe()` 列出每份临时表的对齐结果**（`文件名 → 10-25 ~ 10-31`），
   发布前一眼能看出哪份会盖住哪一周。

**实测**

| 项 | 结果 |
| --- | --- |
| 4 份临时表（含 `2026-10-29` 那份）对齐 | 全部 → `2026-10-25 ~ 10-31` ✔ |
| 包内最晚 `ValidTo` | `2026-10-31`（修改前是 `11-04`）✔ |
| 指纹稳定性 | 连算两次相同；改 mtime 后变化；空目录返回 `''` ✔ |
| 发布 | 90 班 / **605 条**（去重掉 39 条同 Key）/ 孤儿 0 ✔ |
| 本机落地 | 90 班 / 605 条，与包完全一致 ✔ |
| 同文件再发一次 | `Skipped=True`、本机 `LocalSkipped=True`（不再重复落地）✔ |
| 防抖状态机 | 指纹 A 稳定→发布；改成 B→只记 pending；再改 C→稳定后发布；共 2 次 ✔ |
| `--ui-check` | 14 个窗口全部 OK ✔ |
| 设置窗口 | 新增「自动发布」一行，底部按钮不被裁 ✔ |

**尚未改动的两个小 bug（用户本轮未选）**

- `UpdateIntervalMinutes` 保存端 0~1440、使用端 `Clamp(5,720)`，值被静默改写；
- "0 = 只在启动时检查一次"没有任何实现。

**注意**：改成对齐后，用户手上的包条数会从 644 变成 605——
那是 39 条同 Key 记录被合并（内容不变，本来就是后改的那份胜出），不是数据丢失。

### 10.8 修「检查间隔值域不一致」（统一到 5~720）2026-10-31 完成

**问题**：保存端允许 `0~1440`，运行期与状态行都 `Math.Clamp(m, 5, 720)`。
于是「设 3 实际按 5 跑」，而设置窗重新打开仍显示 3 —— 用户看到的是程序自相矛盾，
这正是「以为自动更新没生效」的一部分由来。另外 ToolTip 写着「0 = 只在启动时检查一次」，
而 `Clamp(0,5,720) = 5`，**设 0 反而从"只查一次"变成"每 5 分钟无限查"**。

**决定：反向统一到 5~720，而不是放开到 1~720。** 理由：

- 数据新鲜度由发布侧的自动发布保证（30 秒级），检查间隔只决定"本机多久去拉一次"，
  调小到 1~3 分钟收益很小；
- 30 台 × 1 分钟 = 每分钟 30 次 SMB/FTP 登录，学校老 FTP / IIS 可能限流；
- 默认值本来就是 30，风险面不在默认值，而在**已经落盘的小值**——放开会让历史填过
  1~4 的机器一起变快，且没人知道。

**改动（关键是让阈值只有一份）**

| 位置 | 改动 |
| --- | --- |
| `AppSettings` | 新增 `MinUpdateIntervalMinutes = 5` / `MaxUpdateIntervalMinutes = 720` 两个 `const`；`UpdateIntervalMinutes` 注释改写（删除"0 = 只查一次"的说法） |
| `Store.LoadSettings()` | 新增自愈：`NormalizeUpdateInterval(s)` 越界即夹到区间并落盘（幂等；游客/诊断模式不落盘） |
| `Store.NormalizeUpdateInterval()` | 新增，返回是否改动 |
| `UpdateSettingsWindow` 保存 | `Math.Max(0, Math.Min(1440, m))` → `Math.Clamp(m, 常量, 常量)` |
| `UpdateSettingsWindow` ToolTip | 改成"5~720 分钟 / 默认 30 / 调小只影响本机多久拉一次 / 30 台同时设很小时会加重服务器负担 / 发布机改了 Excel 不用动这里" |
| `MainWindow` 两处（`TickUpdate`、`RefreshUpdateStatus`） | 字面量 `5, 720` → 两个常量 |

**核心理由**：`5` 和 `720` 原本在 3 个文件里各写了一遍，改一处忘一处就复发。
现在只有 `AppSettings` 一份，谁也别想再写成字面量。

**实测（隔离目录，9 个边界值）**

| 存入 | 读出 / 落盘 | 二次读 | 结论 |
| --- | --- | --- | --- |
| 3 | 5 / 5 | 5 / 5 | ✔ |
| 0 | 5 / 5 | 5 / 5 | ✔ |
| -7 | 5 / 5 | 5 / 5 | ✔ |
| 1 | 5 / 5 | 5 / 5 | ✔ |
| 5 | 5 / 5 | 5 / 5 | ✔ |
| 30 | 30 / 30 | 30 / 30 | ✔ |
| 720 | 720 / 720 | 720 / 720 | ✔ |
| 721 | 720 / 720 | 720 / 720 | ✔ |
| 1440 | 720 / 720 | 720 / 720 | ✔ |

- 幂等：二次读取不再改动，不会每次启动都重写 `settings.json`
- 其它字段不受影响（班级 / 数据源 / 路径 / 开关 / 周起始日全部保持）
- 真实设置文件（存在 3）用 `--shot updatesettings` 打开，**界面显示 5** —— 显示值即生效值
- `--ui-check` 14 个窗口全部 OK

**未改动**：「0 = 只在启动时检查一次」没有实现，也不再声称支持。
真要做必须改成下拉选项（仅启动时 / 每 N 分钟 / 不自动），因为「0」这个数字位天生有歧义：
设 0 的人通常以为"不自动更新"，但启动时仍会查一次并可能自动应用（没勾"先问我"时）——
**开机会悄悄换课表**。同理 `UpdateStartupDelaySeconds`（保存 0~600、使用 `Math.Max(5)`）也保持现状，0 秒启动检查本就不合适。

### 10.10 临时课表「整周快照」+ 显示设置页整理 + 默认自动登录（2026-11-01）

#### A. 同步时「未标记 调/代 的格子」必须还原成底表原课程

**现场反馈**：临时课表都是一周一份，教务把某个调课取消后（格子里不再写 `(调)`/`(代)`），
教室里那一格还挂着上次的调课 —— 等于"调代课取消不掉"。

**根因**：数据包只在 manifest 里声明"**恰好有改动的那几天**"为清理范围
（`Export` 原逻辑：`min(记录的 ValidFrom) ~ max(记录的 ValidTo)`）。
于是某周如果一条标记都没有、或改动集中在本周而取消发生在下周，
那几天就不在清理范围内，各教室机上的旧 `temp` 记录永远清不掉。
而临时课表本身是**整周快照**：这一周里没被标记的格子，语义就是"回到基础课表"。

**改法**（都不改数据结构，只把"谁说了算"讲清楚）：

| 位置 | 改动 |
| --- | --- |
| `SchedulePackage.Export(..., DateOnly? clearFrom, DateOnly? clearTo)` | 新增两个可选参数：包声明的"完整描述区间"。有值就优先用它做 `OverrideRange` |
| `SourcePublisher.Publish` | `clearFrom/clearTo = min(临时表所在周) ~ max(临时表所在周)+6`，**与有没有标记无关**；`Result.CoveredWeeks` 回传覆盖的周 |
| `SchedulePackage.Apply` | 清除来源收窄为 `temp` / `remote`（新增 `IsReplacableOverride`）——**`basePatch`（长期改课）永不被清**，与 §6.3 的约定一致 |
| `MainWindow.BtnImportTemp_Click` | 本机导入也按整周快照处理，但**只清这份文件里出现的班级**（分年级发两份时不会互相清空），并把"还原了几条"写进状态栏 |
| 界面文案 | 预检、发布确认框、更新完成状态栏都点明"未标记 调/代 的格子已还原为底表原课程" |

**为什么要按"周范围"而不是"按格子差集"**：包体只需要一句话（区间），
教室机不需要知道"哪一格被取消了"，`Apply` 现有的"先清区间内旧记录、再写入包内记录"
天然就是整周替换。少一个字段、少一类兼容问题。

### 10.12 覆盖策略 + 权限体系（2026-11-01，1.0.3）

两件事一起做：**主机能不能覆盖教室里手工改的调代课**，以及**谁有资格登录进来改东西**。
前者决定数据包怎么写，后者决定谁能按下那个按钮，分开做必然要改两遍同一批代码。

#### A. 「是否覆盖手动调代」为什么必须随包下发

需求原本是"给主机一个开关"。但 30 台教室机没有回传通道，开关放在哪台机器上只影响那台机器 ——
所以真正的开关只有两个位置可选：**教室机本地设**（等于每台机器各管各的，主机说了不算），
或者**跟着数据包走**（主机选一次，全校生效）。选后者。

| 设置项 | 存在哪 | 谁能改 | 作用 |
| --- | --- | --- | --- |
| `OverwriteManualOverrides` | 发布机 `settings.json` | 管理员 | 决定**往包里写什么**（写进 manifest 的 `OverrideIncludeManual`） |
| `PackageOverwriteManual` | 每台教室机 `settings.json` | 只读 | 收到包后**真正生效**的策略 |
| `PackageRev` | 发布机 | 管理员 | 内容版本号，见 C 节 |

教室机上不允许改这两项 —— 发布机说"覆盖"，某台教室机偷偷改回"保留"，那这台机器从此
和其他 29 台显示不一样，而且没人查得出来。

#### B. 软覆盖：停用，不删除

直接 `RemoveAll` 掉手工调课会造成两个后果：老师发现自己排的课"凭空消失"（连痕迹都没有），
以及一旦主机改回"保留"，那些记录也回不来了。所以命中覆盖时**只打标**：

```csharp
public bool Suspended { get; set; }
public DateTime? SuspendedAt { get; set; }
public string SuspendedBy { get; set; }   // 如「包 11-01 09:20」
```

| 位置 | 改动 |
| --- | --- |
| `LessonOverride.IsActiveOn` | 开头 `if (Suspended) return false;` —— **一处判定，全部显示路径跟着变**（悬浮窗 / 周视图 / 桌面背景 / 打印 / 数据包导出） |
| `SchedulePackage.Apply` | 命中且原本未停用 → 置三个字段（计数 `ManualSuspended`），不 `Remove` |
| `SchedulePackage.Apply` 同 Key 去重 | `RemoveAll(x => x.Key == o.Key)` 会顺手吃掉停用记录 → 改成 `&& !x.Suspended`，否则"停用了但下次同步又被包内记录删掉"，恢复入口变空 |
| `OverrideExpander.SuspendedFor` | 按班/按周列出停用记录，供恢复窗口用 |
| `SuspendedOverridesWindow` | 「数据管理 → 恢复被主机停用的本机调课…」逐条或全部恢复；策略仍是"覆盖"时二次提醒"下次同步会再次停用" |

**永久排除 `basePatch`**：那是"改在原始课表上的长期改课"，性质上等于改了底表，不属于本机临时行为。
`IsImportSource` 只认 `temp` / `remote`，覆盖判定对 `basePatch` 直接 `return false`。

#### C. ★ Rev 必须参与摘要（否则策略永远下发不出去）

`DataSha256` 原本只算包里的**文件**。策略开关只改 manifest 的几个布尔位，一个文件都不动
→ 摘要不变 → 各机比对后认为"已是最新" → 永远不 Apply → 主机改了策略，全校毫无反应，
而且程序不会报任何错。

修法：`ComputeDataSha(files, rev)` 里 `sb.Append("rev:").Append(rev)` 打头，让 Rev 成为摘要输入的一部分。

发布侧（`SourcePublisher.Publish` / `UpdateService.PublishCurrent`）：

```csharp
rev = Math.Max(setNow.PackageRev, oldManifest?.Rev ?? 0);
bool policyChanged = old.OverrideIncludeManual != includeManual
                  || old.OverrideAuthoritative != authoritative;
if (policyChanged) rev = Math.Max(rev + 1, old.Rev + 1);
```

即：Rev 单调不减；策略一动就 +1。`remoteJsonEarly` 复用给后面的导出，不多走一次 FTP 往返。

> 换策略 → Rev+1 → 摘要变 → 各机重新下载 → Apply。这条链子任何一环断开，功能就是死的。

#### D. 三类角色

| 角色 | 常量 | 能做什么 | 典型账号 |
| --- | --- | --- | --- |
| 管理员 | `admin` | 改全部班、导入/清除数据、发布与自动更新设置、管理账号 | 年级组长 / 电教老师 |
| 班主任 | `teacher` | **只改自己班**（`ClassNames`）的课表，可编辑作业/缺交；不能发布、不能管理账号 | 各班班主任 |
| 电教管理员（学生） | `student` | 只能控制本机显示（开关悬浮窗、切显示日）；不能改任何数据 | 教室机日常身份 |

**判定必须集中**。全校有 10 处调用 `Store.SaveOverrides`，每处各写一遍 `if (isAdmin)` 早晚漏一处，
而且漏的那处通常最难发现。统一走 `UserSession`：

```csharp
public static bool CanEditClass(string? className) {
    if (_current == null) return false;          // 游客：只能看
    if (IsAdmin)   return true;
    if (IsTeacher) return _current.OwnsClass(className);
    return false;                                 // student
}
```

接入点：`WeekView.OpenArrangeEditor / ApplyDrag / ClearCell / BtnClearAll_Click`、
`LessonOverrideWindow.BtnSave_Click`、`ScheduleWindow.OpenEditor / ApplyDayDrag`。
`ScheduleWindow` 另外做了 3 秒节流（`TipDeny`）—— 穿透态下连拖几下，否则弹一屏提示框。

界面按钮统一由 `MainWindow.ApplyPermissions()` 一次性置灰 + 写 tooltip，
覆盖导入 / 清除 / 导出包 / 导入包 / 备份 / 自动更新设置 / 发布 / 恢复停用 / 管理账号。
顺带补上了一个老洞：`PublishEnabled`（"这台是发布机"）以前谁都能勾，等于谁都能覆盖全校课表，
现在这个页面本身就只有管理员能打开。

#### E. 密码只存哈希

```
PBKDF2-SHA256, 100_000 次迭代, 每条账号独立随机盐(16B), 输出 32B → Base64
```

用户表要随包下发到 30 台机器，明文密码等于把全校账号贴在每台机器侧面。
`PasswordHasher.Verify` 用 `CryptographicOperations.FixedTimeEquals` 比较，避免提前返回的时序差。

「找回密码」因此只能改成「重置」：哈希不可逆，验证通过后让管理员**设一个新密码**，
界面上明说"为安全起见密码不以明文保存、无法查看"。

#### F. 用户表随包下发 + 危险包拦截

`users.json` 作为**可选文件**进包（`PackageFile = "users.json"`），只带用户名 / 哈希 / 盐 / 角色 / 班级，
`UserBook.UpdatedAt` 打包时**不填** —— 包内任何 `DateTime.Now` 都会让摘要每次都变。

| 防护 | 行为 |
| --- | --- |
| 包内用户表一个启用中的管理员都没有 | 拒绝应用，保留本机用户表，`Warnings` 里写明原因 |
| 条目缺用户名 / 哈希 / 盐 | 丢弃该条（宁可少一个账号，不可进一个空密码账号） |
| 角色字符串非法 | 降级为 `student`（解析失败时给最小权限，不是最大） |
| 旧包没有 `users.json` | `UserCount = 0`，本机用户表原样不动 |

#### G. 老数据迁移

旧版是 `settings.json` 里一对 `Username` / `Password`（明文）。升级时：

- 原账号 → **管理员**，明文转哈希（不然升完级老师发现改不了任何设置）；
- 另建 `local`（`student`，密码 `000`）→ 教室机开机身份；
- `AutoLogin` **只换凭据不动开关**：用户以前主动取消过自动登录的，升级不该又给他打开；
  关着的状态下顺手把旧的 `AutoLoginPassword` 清空。

★ `LoadUsers()` 的迁移写盘必须走 `ForceWrite`：这一步发生在"登录成功、打开 `EnablePersistence`"之前，
走普通 `Save*` 会被开关挡掉 → `users.json` 永远不存在 → 每次启动重新迁移 → 盐每次不同
→ 自动登录必然失败。实测"二次读取不再迁移"确认幂等。

★ 反过来，`--ui-check` / `--shot` 这类诊断模式必须**一次都不许写盘**（`Store.SuppressWrites`），
否则在教室机上截个图就把用户表迁移做了、顺手改了人家下次启动的身份。
`SaveUsers` 里原先只判 `EnablePersistence`，漏了这条，已补。

#### I. 边界（写清楚，别当成安全机制）

- 权限只是"界面不给入口"，**能改 `users.json` / `settings.json` 的人照样绕过**。
  离线单机程序的固有边界，防的是误操作和好奇的学生，不是防管理员自己。
- 班主任的 `edits/` 汇聚通道**一期没做**：班主任在本机能改本班课表，但改完不会自动回到主机。
  真要做需要单独设计冲突合并，先留着。`AppUser.SubmittedBy` 字段已预留。
- `basePatch`（长期改课）目前没有任何界面能写出（O6 未做），所以"永不参与覆盖"这条暂时是空架子。
- `remote` 只有判断没有赋值（二一排课预留）。

#### J. 发版时踩到的两个安装脚本坑（1.0.3 打包时修）

| 问题 | 现象 | 修法 |
| --- | --- | --- |
| 静默卸载卡死 | `unins000.exe /VERYSILENT` 不退出、目录还在。`InitializeUninstall` 里的 `MsgBox`（问是否删用户数据）在静默模式下**照样弹窗**，无人值守/批量卸载就永远卡在那一步 | `InitializeUninstall` 开头判 `UninstallSilent` → 直接 `DeleteUserData := False; Result := True; exit;` |
